# 一锅出项目最新方向：真实出处一锅菜饭菜谱收集方案

> 用途：记录最新产品方向、Kimi 评审结论与执行边界  
> 日期：2026-08-02  
> 评审状态：Kimi 首轮评审意见已采纳，等待一致性复核  
> 当前阶段：只做菜谱资料收集与核验；不开发新交互、不部署生产版

## 一、这次为什么重新收敛

一锅出此前先后尝试过食材选择、自由组合、菜谱模板、Planner、DeepSeek 生成、份数与忌口等功能。实际体验暴露出一个根本问题：当真实菜谱基础不足时，技术层会为了覆盖用户输入而机械组合食材，最后出现“白菜豆腐焖饭”“番茄大米酸香主食锅”等项目自创名称，菜名、地域身份和传统做法都缺少可靠出处。

这不符合产品最初目的。用户需要的是一道真实存在、好吃、方便、能够作为一顿饭的一锅主餐，而不是系统为了显得聪明而拼出一个名称。

因此，当前阶段回到最基础的一步：**先把真实的一锅菜饭菜谱收集清楚，再讨论选择食材、个性化推荐或 AI。**

### 1.1 原 5 人 Pilot 的处理

原定 5 人 Pilot 在发放链接前中止。5 位招募对象从未收到测试链接，也没有留下需要履行的测试承诺。

中止原因不是等待、报错或其他一般技术问题，而是产品负责人亲自体验后确认了更根本的产品缺陷：原版本虽然能够生成可执行步骤，但大量菜名和食材组合缺少真实菜谱身份，无法建立“这是一道真实、值得做的菜”的信任。已经确诊的根本问题不应继续交给真实用户重复验证。

冻结的 Preview 构建只保留为历史构件，用于回溯旧技术路线，不再推广、不再作为 Pilot 入口。5 人真实用户验证并未取消，而是后移到 `executable` 菜谱的厨房验证阶段。

## 二、当前唯一目标

建立一份可持续扩充、逐条有真实出处、事实边界清楚的一锅菜饭目录。

建设顺序固定为：

```text
真实菜名与地域身份
→ 独立外部来源
→ 核心食材与传统流程
→ 用量、液体、时间与安全事实
→ 家庭器具适配
→ 人工审核和实际厨房验证
→ 极简“给我一道”页面
```

在目录形成足够密度、关键事实闭合以前，不用 Planner 或 AI 自由组合来弥补菜谱不足。

## 三、第一阶段怎样理解“一锅出”

### 3.1 当前聚焦范围

第一阶段聚焦**咸味米饭主餐**：

- 米饭是成品的主食主体；
- 至少一种主要配菜与米进入同一锅，或处于同一个连续成饭流程；
- 成品能够独立作为一顿主餐；
- 菜名、地域身份或厂商正式配方名称有独立来源；
- 传统器具不限于电饭煲，也可以是电锅、砂锅、铜锅、罗锅、铁锅等；
- 新疆抓饭等虽然传统器具不同，但整体流程与“一锅完成主食和配菜”的目标一致，可以纳入；
- 需要预处理、先炒、焯水或中途开盖加料的做法可以研究，不能仅因不是“所有东西一次放入”就排除。

这一定义强调最终结果和连续流程，不把“电饭煲一次按键”教条化为唯一形式。

### 3.2 第一阶段暂不纳入

- 面条、焖面和粉面；
- 普通炖菜、汤锅和火锅；
- 粥、稀饭和汤饭；
- 熟米饭炒饭、烩饭和泡饭；
- 盖浇饭、饭团、包饭等后组装食品；
- 甜米食和甜点；
- 只有项目自创名称、没有独立外部出处的自由组合菜谱。

这些边界是为了先把一个垂直品类做好，并不是永久否定其他一锅主餐。

“剩饭一锅”登记为未来独立品类，不并入当前首批。只有同时满足以下条件时，才允许重新评估是否开启：

1. 候选必须是具名菜谱，且有充分独立来源；
2. 当前首批 12–15 道生米成饭菜谱已经完成事实闭合；
3. 熟米饭二次烹饪所需的火候、器具和安全事实另建独立合同，不借用生米成饭规则。

## 四、营养与家庭价值原则

产品目标不是只把米和任意配菜煮在一起，而是尽可能兼顾方便、味道和营养结构。

理想结构：

- 碳水主食；
- 有实际分量的蛋白质，如肉、蛋、豆腐或豆类；
- 有实际分量的蔬菜、菌菇或豆类，提供膳食纤维与食材多样性。

可接受结构：

- 米饭 + 蛋白质；或
- 米饭 + 蔬菜、菌菇或豆类。

不适合作为默认推荐：

- 只有米饭和土豆等淀粉食材，主要营养角色仍然只有碳水；
- 只有单一营养角色，不能独立承担一顿主餐。

真实地方菜即使营养结构较单一，也可以保留其文化与研究价值，但不能为了提高营养等级擅自加入来源没有的肉、豆腐或蔬菜，也不能直接进入未来的默认推荐池。

## 五、什么才算“真实出处”

### 5.1 来源优先级

1. 政府、地方志、地方标准、农业或文化主管部门；
2. 原始菜谱书、公共领域或明确授权的菜谱资料；
3. 电饭煲厂商正式说明书或官方菜谱，但主要用于证明厂商配方的器具、程序、水位、用量和流程；不能单独证明传统菜名的地域身份或传统原方；
4. 大学、医院、行业组织的正式食谱资料；
5. 可信媒体或餐饮机构的原创内容，作为补充证据；
6. 社交媒体、聚合站、RecipeDB 和开源仓库只作发现入口，不能自动成为生产授权或完整做法的唯一依据。

项目自身网站、仓库文档和历史生成结果不能给自己作证。

### 5.2 来源只能证明它实际写明的事实

每个来源都要标注它能够支持哪些范围：

- `identity`：真实菜名、地域或菜系；
- `ingredients`：核心食材结构；
- `quantity`：固定食材用量；
- `liquid`：米水或有效液体比例；
- `process`：投料顺序与关键技法；
- `appliance`：器具、程序或水位线；
- `time`：制作时间；
- `safety`：肉、禽、蛋、海鲜等熟制安全要求。

一条只提到菜名的地方文化文章，不能顺带证明克数、米水比例和电饭煲做法。可以使用多条来源共同闭合一道菜，但每个关键事实都必须能追溯。

当两条来源对用量、液体、时间、顺序或器具事实存在冲突时：

1. 两种说法都保留，并分别绑定来源，不得取平均值或挑选更顺眼的数字；
2. 传统身份和原技法优先参考原产地、原技法或更接近原始记录的来源；
3. 厂商资料只对其具体型号和厂商配方负责，不覆盖传统原方；
4. 无法由来源裁决的差异必须进入厨房验证清单；
5. 冲突未解决前不得标为 `executable`。

### 5.3 传统原方与家庭适配必须分开

- 传统名称、核心食材和关键技法有来源支持时，按原身份记录；
- 若把砂锅、铁锅或铜锅做法改为电饭煲版，必须单独标记为“家庭适配”；
- 适配不能擅自改变主要食材、比例、顺序和安全边界；
- 原器具来源只证明原器具事实，不能证明电饭煲参数；
- 一切转换参数，包括水量、程序、防糊底处理和投料时机，都必须经过对应电饭煲版本的实际制作验证后才能公开，无一例外；
- 只完成文字推导、比例换算或模型推演的适配仍停留在研究阶段，不能当作公开可执行菜谱。

### 5.4 版权边界

只提取菜名、事实、结构和高层技法，不复制第三方完整步骤、图片、视频、版式或大段原文。未来用户可见步骤需要基于已核验事实重新组织，但重新表达不能改变事实。

## 六、每道菜的状态怎么推进

```text
discovered
→ identity_verified
→ recipe_fact_checked
→ executable
→ preview_ready
→ kitchen_observed
→ production_approved
```

- `discovered`：发现候选名称，尚未核实；
- `identity_verified`：真实菜名与地域身份已有可靠证据；
- `recipe_fact_checked`：核心食材和关键流程已有证据；
- `executable`：固定用量、液体、流程、时间和安全边界完整；
- `preview_ready`：机器检查和人工内容审核通过；
- `kitchen_observed`：已有真实家庭按该版本完成制作的记录；
- `production_approved`：用户批准后才能进入正式版本。

脚本不能自动把菜谱越级。缺少关键事实时就诚实停在当前状态。

## 八、目前最重要的工作，不是什么

当前不做：

- 用户选择食材；
- 根据用户食材自由组合菜名；
- Planner、模板或推荐算法扩展；
- DeepSeek 生成；
- 份数、忌口、模式和多锅规划；
- 账号、用户画像、营养追踪、收藏和历史；
- 为了凑数量而给每个省硬造一道菜；
- 把 32 道候选宣传成已经能照做的 32 道完整菜谱。

当前真正要做的是：

1. 按地域和技法框架继续发现真实具名菜饭；
2. 优先补齐现有 32 道的关键事实缺口；
3. 去重别名、地域变体和同技法小变化；
4. 逐道明确来源能够证明什么；
5. 建立固定批量、液体、时间和安全合同；
6. 对家庭电饭煲适配单独留证和验证；
7. 形成第一批真正可执行、可预览、可厨房验证的菜谱。

第一批锁定 12–15 道、覆盖至少 6 个地域或技法家族。研究设置固定检查点，防止无限打磨；但时间盒只是决定继续、替换或缩小批次，**时间到了只能缩小批次，不能降低证据门槛。**

执行优先级与逐道四合同进度统一记录在[《首批12道菜谱事实闭合执行清单》](./首批12道菜谱事实闭合执行清单.md)中，不再维护第二份口径不同的进度表。

## 九、未来页面方向（目录成熟后再做）

未来页面保持极简：

```text
打开页面
→ 点击“给我一道真实菜饭”
→ 展示真实菜名、地域、固定做法和出处
→ 点击“换一道”
```

首屏不提供食材输入、份数、忌口或模式。页面不调用 DeepSeek，也不自由组合。

已经确认的展示原则：

- 随机推荐只能来自达到相应公开门槛的菜谱；
- 当前若做资料预览，最多只能从 15 道 `recipe_fact_checked` 中展示其已核验事实，不能伪装成完整可执行做法；
- 其余 17 道只能放在“研究中”目录，清楚展示资料缺口；
- 同一轮先不重复，全部看过后才能重新开始；
- 每一道都有直接原始来源入口；
- 来源不足时宁可不提供步骤，也不让系统补写。

页面开发至少等待第一批 12–15 道达到 `preview_ready`。进入正式版本前，每道还必须至少有一次真实家庭按当前版本完成制作的记录，进入 `kitchen_observed`；原 5 人 Pilot 名单届时可以用于厨房验证，但不能拿研究记录让用户替项目补齐事实。

## 十、Kimi 评审结论与本轮采纳项

Kimi 对“内容先行、技术后置”的总方向表示通过。本轮正式采纳：

1. 原 Pilot 在链接发放前中止，历史 Preview 不再推广；真实用户验证后移到厨房实做阶段；
2. 熟米饭炒饭不并入当前目录，只登记为满足明确开启条件后的未来独立品类；
3. 原器具事实不能推导成电饭煲参数，任何适配必须实做后才能公开；
4. 增加来源冲突裁决规则，冲突未解决不得进入 `executable`；
5. 厂商说明书主要证明具体厂商配方、器具、程序和水位，不证明传统身份；
6. 第一批锁定 12–15 道、至少 6 个地域或技法家族，全部闭合用量、液体、时间和安全四合同；
7. 每道菜必须至少有一次真实家庭制作成功，才能进入 `kitchen_observed`；
8. 研究设置时间盒，但只能据此缩小或调整批次，不能降低来源与可执行门槛。

首批优先顺序：

- 第一组：上海咸肉菜饭、腊味煲仔饭、手抓饭、咖喱鸡肉饭、冬菇滑鸡饭；
- 第二组：高丽菜饭、南瓜饭、香菇筍仔飯、肉糜青菜饭、肉粘饭、孔干饭、鲜蔬竹笋饭；
- 第三组：其余文化价值较高、但当前事实缺口较大的条目，继续保留在研究目录，不赶首批。

首批执行分三阶段：

1. 事实闭合：为第一、第二组建立来源矩阵和四合同，达到 `executable`；
2. 厨房验证：由真实家庭按固定版本实做并记录结果，达到 `kitchen_observed`；
3. 极简页面：只展示已通过相应门槛的真实菜谱，不恢复 Planner 或 AI 自由组合。

## 十一、不可越过的底线

1. 不拿项目自创名称冒充真实菜谱；
2. 不拿“菜名来源”冒充完整做法来源；
3. 不复制第三方完整步骤和图片；
4. 不让 AI 决定菜名、核心食材、比例或安全边界；
5. 不为了营养好看而篡改传统原方；
6. 不为了数量给地域硬凑菜；
7. 不把研究候选宣传成可执行菜谱；
8. 未经人工审核和厨房验证，不部署为正式版。

一句话总结：**先把真实存在、来源可靠、做法事实闭合的一锅菜饭逐道收集好；产品以后只负责把这些真实菜谱简单地交给用户，不再用技术自由组合掩盖内容不足。**
