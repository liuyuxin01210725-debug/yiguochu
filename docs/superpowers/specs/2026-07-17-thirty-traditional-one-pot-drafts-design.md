# 30 道传统一锅原创草案扩展设计

## 目标

将现有 30 道、仅作文化事实研究的地域候选菜，逐一建立为项目原创的试做草案。结果是一个可编辑、可试做、可审核的 30 道草案池，为后续逐批增加手机端正式菜谱做准备。

本次不改变手机端、worker 或本地代理的运行时数据源；用户当前可调用的正式库仍为 9 个家族、12 道基础菜谱。

## 范围与边界

- 扩充 `tools/data/recipe-drafts.json`：每个候选菜恰有一条 `status: "draft"` 的原创草案，共 30 条。
- 每条草案继续关联唯一的 `candidate_id`，只能使用候选册中仍为 `candidate` 状态的条目。
- 草案只给编辑、试做与人工审核使用。不得被前端、worker、本地代理加载，不得作为线上菜谱展示或生成依据。
- 不复制或改写第三方食谱的具体食材表、克数、时长、顺序或完整做法；候选册的地域、菜名、常见核心食材和高层技法只用作可追溯的创作方向。
- 本次不向 `tools/data/recipe-library.json` 增加菜谱，不部署，不触碰营养权威数据逻辑。

## 数据与校验设计

每条草案沿用现有结构：菜名、地域、形态、适用份数、核心/可选食材、原创比例逻辑、高层技法、明确替换槽位、试做要求，以及安全和质量门槛。

发布闸门从当前“固定校验六道”改为“固定校验全部 30 道”：

1. 每个预期草案 ID 必须存在，且严格映射到指定的候选 ID；
2. 不允许重复的草案 ID 或候选 ID；
3. 被关联候选必须仍是 `status: "candidate"`；
4. 缺少、错连或额外映射均应在检查中失败；
5. 既有 schema 校验继续约束所有字段、替换槽位和安全门槛。

这样可以防止“写了 30 条但偷换成同一种菜”或后续误把草案接入生产库。

## 风险分层与后续晋升

草案按候选册的 `risk_level` 分三层执行试做，而不是按数量直接放行：

- low：先完成米面熟度、口感、一锅完成性和结构审核；
- moderate：额外核验火候、吸水/出水、分步下锅与替换边界；
- high：在上述基础上，逐项验证生肉、禽蛋、海鲜、骨刺、豆角、腌腊或地方食材的原料身份、熟制证据、过敏原、盐分和保存风险。

后续每一批拟进入正式库的菜，仍必须完成真实试做日志、人工审核、项目自有 canonical 来源页，以及现有 Phase A 的来源、回归与人工评审闸门。30 道草案不代表 30 道已上线菜谱。

## 测试与验收

实现完成后，以下命令必须通过：

```bash
node --test tools/tests/recipe-drafts.test.mjs
node tools/check-recipe-drafts.mjs
node tools/check-recipe-candidates.mjs
node tools/check-recipes.mjs
```

验收结果应明确为：草案 30 道、生产可用 0 道；候选 30 道、生产可用 0 道；正式库仍为 9 个家族、12 道基础菜谱。
