# 一锅出菜谱原型库与生成约束设计

日期：2026-07-14

状态：待用户书面审核

目标版本：第一阶段 10–15 个全球一锅菜原型

## 1. 背景与问题

当前线上菜谱由 DeepSeek 根据用户目的、份数、库存食材和忌口直接生成。营养数值已有“台湾食药署库 → 前端本地库 → AI 估算”的权威纠偏，但菜谱搭配、味型、下锅顺序和食品安全仍主要依赖模型本身。

现有提示词允许“不合适时不要为了全用而牺牲可吃性”，但换菜流程又要求继续保留并用上库存食材。前端评分主要检查步骤数、时间、主食存在性、忌口和基本营养，不足以阻止以下问题：

- 为了使用全部库存食材而强行组合；
- 食材列出但没有真正进入制作步骤；
- 肉类、海鲜没有明确熟制；
- 水量、主食比例和下锅顺序不合理；
- 菜名和口味说明听起来合理，但没有可靠菜谱原型支撑。

## 2. 设计目标

第一阶段不追求海量菜谱，而是建立一套小而可靠的全球一锅菜原型库，使生成过程从“模型自由创作”改为“检索成熟原型后有限改编”。

成功标准：

1. 常见家常食材输入能够命中至少一个已审核原型；
2. 系统可以主动舍弃不适合当前原型的库存食材，并说明原因；
3. 所有主料都在步骤中出现，生肉和海鲜都有明确熟制动作；
4. 用户能看到简短的“搭配依据”和“本次未使用的食材”；
5. 不把授权不清楚或限制商业使用的数据部署到线上；
6. 原型检索与规则校验本身不增加模型调用；仅沿用现有失败重试机制，控制延迟和 DeepSeek 成本。

## 3. 非目标

第一阶段不做：

- 复制或部署 RecipeDB 全量数据；
- 实时抓取第三方菜谱网站；
- 训练或微调 DeepSeek；
- 建立百万级向量数据库；
- 用户长期饮食追踪；
- 根据用户行为自动改写原型；
- 宣称“食物相克”或未经证实的健康禁忌。

## 4. 来源与授权边界

### 4.1 RecipeDB 的定位

RecipeDB 只作为内部研究和分类参考，不进入线上运行包，不在生成请求时实时调用，也不复制其完整做法。其数据库采用 CC BY-NC-SA 3.0，含非商业和相同方式共享限制；小红书涨粉、引流等使用场景可能具有商业目的，因此不把 RecipeDB 数据作为线上生产数据。

内部研究允许做的事情：

- 了解全球菜系、烹饪方法和菜谱结构的分类方式；
- 发现值得进一步核对的一锅菜原型；
- 记录原始页面链接、菜名和待验证假设；
- 学习如何把食材、技法、器具和地域做结构化表达。

内部研究不允许做的事情：

- 批量抓取后随应用部署；
- 复制完整配方或做法后换一种说法公开输出；
- 把 RecipeDB 原始数据当成可商用训练集或检索库；
- 因为做了“二创”就移除其非商业限制。

### 4.2 生产可用来源

每张上线原型卡必须至少有一个“生产可用”来源或经过自有测试，不得仅以 RecipeDB 为依据。候选来源按条目逐一审核：

- Wikibooks Cookbook：通常为 CC BY-SA 4.0，需逐页确认、署名、标明修改并满足相同方式共享；
- Nutrition.gov、MyPlate、SNAP-Ed 等政府或合作推广机构页面：逐页确认权利声明和来源；
- 公版烹饪书：确认具体版本已进入公版并记录出处；
- 团队自有配方和实际试做记录；
- 以后获得明确许可的其他来源。

“GitHub 仓库有开源许可证”只证明代码或仓库作者拥有的内容如何许可，不自动证明其抓取的第三方菜谱可以重新授权。来源不清楚的仓库一律标为待审或拒绝。

### 4.3 来源审计状态

每个来源使用以下状态之一：

- `approved`：可进入生产原型库；
- `research_only`：仅作内部发现和分类参考；
- `pending`：权利或出处尚未核清；
- `rejected`：不得使用。

只有 `approved` 来源可以支撑上线原型。

## 5. “后台研究”的实际流程

后台研究是一次性、离线的内容整理，不是用户每次生成时访问 RecipeDB。

### 5.1 发现

按“一锅出”场景检索代表性菜式：一锅炖、焖饭、炊饭、汤面、咖喱、豆类锅、烩饭和适合分装复热的锅物。RecipeDB 可用于发现名称、地域和技法，但发现结果先进入研究清单，不直接上线。

### 5.2 交叉核对

研究人员从生产可用来源核对以下事实：

- 核心食材和可替换食材；
- 味型基础；
- 烹饪先后顺序；
- 液体与主食的比例范围；
- 哪些食材会导致味道、质地、出水量或成熟时间冲突；
- 肉类、蛋类、豆类和海鲜的安全节点；
- 是否真正适合“一锅完成”。

“不建议组合”只能基于口味、质地、水量、成熟时间或食品安全，不使用没有证据的“食物相克”说法。

### 5.3 原型化

不保存大段原始菜谱文本，而是整理成我们自己的结构化原型卡。每张卡代表一个可扩展的烹饪结构，不等于一道固定菜。

### 5.4 人工审核与试做

上线前至少完成结构审核；高风险或比例敏感的原型应实际试做。试做结果记录用量、锅具、时间、成品状态和修订原因。

## 6. 原型卡数据模型

原型库建议存为独立的结构化 JSON，由构建脚本校验后随 Worker 部署。核心字段如下：

```json
{
  "id": "curry-stew-basic",
  "name": "家常咖喱炖锅",
  "status": "approved",
  "cuisines": ["南亚", "日式家常"],
  "forms": ["一锅炖", "焖煮"],
  "purposes": ["quick", "pantry", "batch"],
  "core_roles": ["蛋白质", "耐煮根茎", "芳香底料"],
  "optional_roles": ["菌菇", "豆类", "椰奶或乳制品"],
  "discouraged": [
    {
      "role": "大量易出水叶菜",
      "reason": "会稀释酱汁，若使用应少量并在后段加入"
    }
  ],
  "flavor_base": ["咖喱香料", "芳香底料", "脂肪", "盐味"],
  "technique": ["蛋白质熟制", "炒香底料", "加液炖煮", "收汁"],
  "ratio_rules": ["主食同锅时必须单独计算吸水量"],
  "safety_rules": ["禽肉和海鲜必须在步骤中明确完全熟制"],
  "source_refs": [
    {
      "title": "来源标题",
      "url": "https://example.com",
      "license": "许可名称",
      "usage": "approved"
    }
  ],
  "review": {
    "structure_checked": true,
    "tested": false,
    "updated_at": "2026-07-14"
  }
}
```

生产卡禁止出现无来源、无理由的绝对判断。来源链接、许可和审核日期为必填字段。

## 7. 第一阶段原型范围

首批控制在 10–15 个原型，优先覆盖常见食材和不同味型：

1. 中式家常焖饭；
2. 中式番茄炖锅；
3. 中式菌菇豆腐锅；
4. 日式炊饭；
5. 日式咖喱炖锅；
6. 韩式家常锅物；
7. 东南亚椰香咖喱；
8. 印度豆类咖喱；
9. 地中海番茄豆类炖锅；
10. 墨西哥豆肉饭；
11. 西式奶油炖锅；
12. 汤面或米粉锅；
13. 粥、杂粮粥和咸粥；
14. 适合分装复热的豆肉炖锅；
15. 其他经来源审核后补充的高覆盖原型。

具体名单以来源授权和食材覆盖率为准，宁缺毋滥。

## 8. 线上生成架构

### 8.1 运行组件

1. **食材规范化器**：把用户输入映射为食材名称、类别、状态和角色；
2. **原型检索器**：从 10–15 个本地原型中选出最匹配的 3 个；
3. **兼容性决策器**：选择适合当前原型的食材子集，输出未使用食材及原因；
4. **生成约束包**：把原型、必须规则、可选替换和安全节点压缩后交给 DeepSeek；
5. **结果验证器**：检查步骤完整性、忌口、安全、液体规则和原型一致性；
6. **营养纠偏层**：继续沿用现有台湾库、本地库和估算标记机制；
7. **前端说明层**：展示“搭配依据”和“本次未使用”。

第一阶段数据量很小，使用确定性关键词和角色匹配即可，不引入向量数据库。

### 8.2 数据流

```text
用户目的、份数、食材、忌口
  → 食材规范化与忌口硬过滤
  → 原型检索 Top 3
  → 选择一个原型与兼容食材子集
  → 生成约束包
  → DeepSeek 一次生成
  → 结构、安全、步骤和原型校验
  → 台湾库 / 本地库营养纠偏
  → 返回菜谱、搭配依据、未使用食材
```

### 8.3 原型匹配原则

匹配分数考虑：

- 核心角色覆盖率；
- 用户目的是否适合该原型；
- 锅具和时间是否满足；
- 是否触发明确的质地、出水或成熟时间冲突；
- 忌口过滤后是否仍能形成完整主餐；
- 最近菜谱和食材轮换。

不能命中高置信原型时，不允许模型进行高风险自由组合。系统优先减少食材、选择保守的已知原型；仍不成立时，明确告诉用户哪些食材建议分开处理。

## 9. 生成契约调整

Worker 返回结构新增：

- `prototype_id`：使用的原型；
- `basis_level`：`classic` 或 `adapted`；
- `pairing_basis`：用户可读的一句话搭配依据；
- `used_pantry`：本次使用的库存食材；
- `unused_pantry`：未使用食材及原因；
- `safety_checks`：已覆盖的关键安全动作；
- `validation_flags`：仅供内部诊断，不直接展示。

提示词必须取消“换菜时仍要保留并用上全部库存食材”的要求，统一为：优先使用相容食材，不合适的可以舍弃并说明原因。

本地调试代理 `ai_proxy.py` 与 `worker/src/worker.js` 必须同步更新，避免本地和线上生成行为漂移。

## 10. 结果验证规则

验证器至少检查：

- 忌口或过敏食材不得出现；
- 菜名中的核心食材必须存在于食材表和步骤；
- 非调味食材必须在步骤中被处理；
- 禽肉、猪肉、海鲜、蛋等高风险食材必须有明确熟制动作；
- 米、面、豆类等主食的处理方式与标题一致；
- 原型要求的关键技法不得缺失；
- 一锅菜不得暗中要求另起多锅；
- 不得声称没有来源支持的健康功效或“食物相克”；
- `unused_pantry` 中的理由必须具体且中性；
- 营养数值继续遵守现有权威查表红线。

校验失败时沿用现有的一次质量重生成机制；仍失败则回退到已有安全方案，并记录失败原因。第一阶段不增加独立的“审核模型”调用。

## 11. 用户界面

结果页默认增加两行短信息：

- **搭配依据**：例如“参考经典咖喱炖锅结构，鸡肉、土豆和胡萝卜适合共同炖煮”；
- **这次没用**：例如“白菜容易出水，本次不放；可另做清炒”。

详细来源放在可展开区域，展示原型名称、来源链接和授权说明。不要用“科学证明最好吃”等过度承诺。

## 12. 错误处理与降级

- 原型库加载失败：使用内置最小安全原型，不退回完全自由生成；
- 没有高置信匹配：减少食材后匹配，不能为清库存强行拼接；
- 来源状态不是 `approved`：构建失败，禁止部署；
- 原型字段缺失、ID 重复或理由为空：构建失败；
- DeepSeek 返回缺字段：沿用现有一次重试和应急方案；
- 营养库未命中：继续诚实标记为估算，不因有原型就伪装成权威值。

## 13. 测试与验收

### 13.1 自动检查

新增原型体检脚本，检查：

- ID、必填字段和枚举合法性；
- 上线卡的来源全部为 `approved`；
- 来源链接、许可和审核日期完整；
- 不建议组合均有允许的理由类型；
- 无无依据健康宣称和“食物相克”词句；
- 本地代理与 Worker 的生成契约关键字段保持一致。

### 13.2 固定回归集

建立至少 100 组输入，覆盖：

- 常见肉类、豆制品、鱼虾、叶菜、根茎和主食；
- 明显不适合全放入一锅的组合；
- 素食、无麸质和过敏场景；
- 一人份、多人份和批量分装；
- 快手、清库存、换口味和多做一些；
- 换菜后仍带库存食材的现有路径。

硬性验收：

- 过敏食材出现次数为 0；
- 生肉或海鲜无熟制步骤次数为 0；
- 食材列出但完全未进入步骤次数为 0；
- 因“必须全用”产生的强行组合次数为 0；
- 所有输出都提供搭配依据；
- 原型检索不增加额外 DeepSeek 调用。

### 13.3 人工检查

从回归集中抽取至少 30 组，按“像不像真实菜、味型是否协调、能否一锅完成、步骤能否照做、安全是否清楚”五项审核。比例敏感的原型优先试做。

## 14. 上线与观察

第一阶段先在本地和预览部署验证，再上线主站。上线后只观察匿名、低敏感信号：

- 原型命中率；
- 用户换菜率；
- “开始做”点击率；
- 未使用食材的常见原因；
- 哪些原型经常被换掉；
- 生成和校验失败原因。

不记录原始过敏信息，不把完整库存食材与可识别用户身份绑定。行为数据只用于发现原型缺口和优化顺序，不能未经审核自动修改生产原型。

## 15. 分阶段交付

### 阶段 A：来源与原型基础

- 建立来源审计表；
- 完成首批 10–15 张原型卡；
- 建立原型体检脚本；
- 完成 100 组回归输入。

### 阶段 B：接入生成链路

- Worker 加载并检索原型；
- 修复强制使用库存食材的提示词冲突；
- 扩展生成契约；
- 增加结果验证器；
- 同步本地代理。

### 阶段 C：前端信任说明

- 展示搭配依据和未使用食材；
- 提供可展开的来源与授权信息；
- 完成移动端、PWA、预览域和线上回归。

### 阶段 D：真实反馈后扩充

- 根据用户换菜和开始做等信号补充原型；
- 每次小批量加入并重新跑体检与回归；
- 只有在 40–60 个原型仍不能覆盖长尾需求时，才评估更复杂的检索系统。

## 16. 关键决策摘要

- RecipeDB 是研究参考，不是线上生产库；
- 第一版做 10–15 个原型，不搬运海量菜谱；
- 原型来自许可清楚的来源或自有测试；
- 检索后再生成，允许舍弃不合适食材；
- 生成后做确定性安全和步骤检查；
- 原型检索和规则校验不新增模型调用，只沿用现有失败重试；
- 先验证质量提升，再逐步扩充到 40–60 个原型。
