# 一锅出：真实出处菜谱目录优先版设计

日期：2026-08-02

状态：用户已确认产品方向；本文件等待用户最终审阅后进入实施计划

适用范围：Draft PR #1 与 `recipe-validation` Preview；不授权合并 PR 或部署 production

## 1. 决策摘要

一锅出暂停食材选择、自由组合、Planner、模板扩展和个性化推荐。当前唯一任务是建立一份有独立真实出处、能够逐条核验的一锅出菜谱目录。

产品按以下顺序建设：

```text
真实菜名与地域身份
→ 独立外部来源
→ 核心食材与传统流程
→ 用量、液体、时间和安全事实
→ 家庭器具适配
→ 机器校验
→ 极简“给我一道”页面
```

在目录完成第一轮系统核验前，不继续优化现有推荐算法和食材规划体验。

## 2. 当前唯一产品承诺

未来面向用户的页面只做一件事：从已经核验的真实一锅出菜谱中给出一道完整菜谱。

首屏最终形态只有：

- 产品名称与一句用途说明；
- `给我一道一锅出` 主按钮。

结果页只保留：

- 真实菜名；
- 地域或菜系；
- 食材与用量；
- 家庭可执行步骤；
- 器具与预计时间；
- 过敏原和熟制提醒；
- `查看真实出处`；
- `换一道`。

首屏不再提供份数、食材、忌口、模式、意图、账号、历史、收藏、营养目标或其他设置。菜谱使用其已经审核的固定标准份量；需要变更份量的能力以后单独设计。

## 3. 一锅出收集范围

### 3.1 纳入范围

第一阶段继续聚焦咸味米饭主餐：

1. 米饭是成品主食主体；
2. 至少一种主要配菜与米进入同一锅，或处于同一个连续成饭流程；
3. 成品能够作为一顿主餐；
4. 菜名、地域身份或厂商正式配方名称有独立出处；
5. 传统器具可以是电饭煲、电锅、砂锅、铜锅、罗锅、铁锅或其他器具；
6. 传统流程与电饭煲基本相近时，可以研究家庭电饭煲适配版，但必须明确哪些是来源事实、哪些是项目适配；
7. 上海菜饭、闽南咸饭、台湾菜饭、新疆抓饭、宁夏肉粘饭、云南豆焖饭、煲仔饭等均可进入研究目录。

### 3.2 暂不纳入

- 面条、焖面和粉面；
- 普通炖菜、汤锅和火锅；
- 粥、稀饭和汤饭；
- 熟米饭炒饭、烩饭和泡饭；
- 盖浇饭、饭团、包饭等后组装食品；
- 甜米食和甜点；
- 只有项目自创名称、没有独立外部出处的自由组合菜谱。

### 3.3 “所有菜谱”的可执行定义

项目不得宣称穷尽了互联网、民间或中国历史上的全部一锅出菜谱。“所有”在工程上定义为：

- 全国地域框架中的每个区域都经过主动检索；
- 找到的符合边界的真实菜名全部进入候选账本；
- 暂时没有可靠来源的区域明确记录为空白，而不是硬造菜名；
- 同一道菜的别名与地域变体去重后保留关系；
- 每一轮发布都明确目录版本、检索日期和覆盖范围；
- 后续发现新菜谱时可以持续增补，但不能把当前目录宣传成绝对完整。

## 4. 菜谱出处红线

### 4.1 独立出处

每道公开菜谱至少需要一条项目外的直接来源。`yiguochu.pages.dev`、本仓库文档和项目自己生成的菜谱页面不能给自己作证。

来源优先级：

1. 政府、地方志、地方标准、农业或文化主管部门；
2. 原始菜谱书、公共领域或明确授权的菜谱资料；
3. 电饭煲厂商的正式说明书或官方菜谱；
4. 大学、医院、行业组织的正式食谱资料；
5. 可信媒体或餐饮机构的原创内容，只作补充证据；
6. 社交媒体、聚合站和 RecipeDB 只作发现入口，不直接作为可执行配方的唯一依据。

每条 `source_refs[]` 可选记录 `evidence_tier`（1–6），用于把“来源质量”与“该来源实际证明的事实范围”分开记账：1–5 表示政府/地方志/标准、原始授权资料、厂商正式资料、正式机构食谱或可信原创报道等可直接核验来源；6 表示聚合页、发布者转载或仅适合发现入口的来源。第 6 级来源可以在来源明确、边界受限时支撑身份或通用技法研究记录，但不得单独闭合可执行配方。

允许保留一个有边界的第 6 级 `process` 技法记录，状态仍可为 `recipe_fact_checked`，但必须在 `evidence_notes` 明示“技法来源待加强”，人类可读目录也必须显示该警告；只要某条记录的 `process` 证据全部来自第 6 级，就不得晋升 `executable`、`preview_ready`、`kitchen_observed` 或 `production_approved`。晋升前必须补入至少一条第 1–5 级、直接支持 `process` 的来源。不得因为第 6 级来源写了数量、时间或器具，就把这些事实自动升级为通用合同。

### 4.2 来源证明范围

来源必须逐项声明能够证明什么：

- `identity`：真实菜名、地域或菜系；
- `ingredients`：核心食材结构；
- `quantity`：固定食材用量；
- `liquid`：米水或有效液体比例；
- `process`：投料顺序与关键技法；
- `appliance`：器具、程序或水位线；
- `time`：时间；
- `safety`：熟制或特殊食材安全要求。

一条只证明菜名的来源，不能同时冒充用量和米水比例依据。不同来源可以共同闭合一份菜谱，但每个事实必须能追溯到具体来源。

### 4.3 版权边界

项目只提取事实、结构和高层技法，不复制第三方完整步骤、图片、视频、版式和长段文字。面向用户的步骤由项目根据已核验事实重新组织；重新表达不允许改变原料、比例、顺序和安全边界。

## 5. 菜谱目录结构

目录使用一个结构化权威源，建议新增 `tools/data/source-backed-one-pot-recipes.v1.json`。研究表和用户页面均由该文件确定性生成，禁止出现两套彼此漂移的菜谱事实。

每道菜至少包含：

```json
{
  "recipe_id": "stable-kebab-id",
  "canonical_name": "上海咸肉菜饭",
  "aliases": [],
  "region_codes": ["CN-SH"],
  "cuisine_family": "jiangnan-vegetable-rice",
  "identity_status": "verified",
  "traditional_vessel": ["铁锅"],
  "core_ingredients": [],
  "fixed_batch": {
    "servings": 3,
    "ingredients": []
  },
  "liquid_contract": {},
  "cooking_sequence": [],
  "time_contract": {},
  "safety_endpoints": [],
  "allergen_labels": [],
  "nutrition_structure": {},
  "cooker_adaptation": {},
  "source_refs": [],
  "status": "research_only"
}
```

`source_refs[]` 的来源对象应尽量包含 `evidence_tier`；省略时表示尚未完成来源分级，不得据此推断为高等级来源。目录生成器会把第 6 级独证的技法警告透传到 Markdown/CSV，避免研究状态被误读成已经可执行。

### 5.1 固定名称

- `canonical_name` 必须能由独立来源证明；
- 不允许用用户食材、模板槽位或算法输出机械拼接菜名；
- 项目进行器具或流程改编时，必须显示“家庭版”“电饭煲版”或“风味版”，不得继续冒充传统原方；
- 地域名只有在来源明确支持时才能进入菜名。

### 5.2 固定批量

第一阶段每道菜只维护一套已经核验的固定标准份量。没有可靠用量、液体、时间或器具合同的条目可以留在研究目录，但不得进入用户可见目录。

Ratio DSL 只能读取结构化数值，不读取自然语言后自行猜测。厂商“水位线”不得擅自换算成通用毫升；来源比例语义不清时必须阻断。

### 5.3 营养结构

目录继续诚实标注：

- A：米饭 + 有实际分量的蛋白质 + 有实际分量的蔬菜、菌菇或豆类；
- B：米饭 + 蛋白质，或米饭 + 蔬菜/菌菇/豆类；
- C：只有单一主要营养角色。

C 级真实菜谱可以保留文化与研究价值，但不进入默认随机推荐池。不得为了提高等级而擅自给传统菜增加没有来源的主要食材。

### 5.4 目录版本与变更纪律

`catalog_version` 是厨房验证、来源审计和用户构建的锚点。任何菜谱条目、来源、来源分级、事实合同、状态、警告或地域覆盖范围发生变化，都必须同时 bump `catalog_version`；只改文档措辞而不改结构化目录时可不 bump，但不得让结构化目录与生成产物使用同一旧版本号冒充新内容。版本号应包含日期和递增修订标记，例如 `source-backed-one-pot-v1-20260804-national-r1`。

## 6. 状态机

每道菜按事实完整度推进：

```text
discovered
→ identity_verified
→ recipe_fact_checked
→ executable
→ preview_ready
→ kitchen_observed
→ production_approved
```

- `discovered`：找到候选名称，尚未核实；
- `identity_verified`：真实菜名与地域身份有据；
- `recipe_fact_checked`：核心食材和关键技法有据；
- `executable`：固定批量、液体、流程、时间和安全边界闭合；
- `preview_ready`：机器门禁和人工内容审核通过；
- `kitchen_observed`：有真实家庭照做记录；
- `production_approved`：用户明确批准后进入正式版本。

状态不得由脚本自动越级。缺任何关键事实时保持原状态。

特别地，`recipe_fact_checked` 仅由第 6 级来源支撑的 `process` 记录属于“有边界的通用技法记录”，必须显示“技法来源待加强”，并停在该状态；没有第 1–5 级 `process` 证据时，任何脚本或人工都不得把它当作可执行菜谱发布。

## 7. 收集框架

菜谱收集按技法与地域家族展开，不要求每省凑数：

1. 江南菜饭：上海、苏南、浙北；
2. 闽南咸饭与糯米饭：泉州、厦门、漳州；
3. 台湾菜饭、炊饭与油饭；
4. 岭南煲仔饭及其具名变体；
5. 新疆抓饭；
6. 宁夏肉粘饭；
7. 云南豆焖饭、火腿焖饭和罗锅饭；
8. 川渝孔饭、洋芋饭的营养合格版本；
9. 西北其他真实米饭一锅主餐；
10. 东北、华北、华中及其他区域中符合米饭主餐边界的具名菜谱；
11. 厂商正式电饭煲菜谱，作为非地域但可执行的补充目录。

同一技法的食材小变化记录为变体，不膨胀成大量虚假“新菜”。

## 8. 收集产物

第一阶段只交付内容资产：

- 结构化候选目录；
- 人类可读的菜名、地域、食材和出处总表；
- 每个地域的检索记录与明确空白；
- 重复菜、别名和家族关系表；
- 可执行事实缺口表；
- 用户可见候选清单。

每条记录都必须能回答：这道菜叫什么、从哪里来、传统上用什么、怎样做、哪些事实已经闭合、哪些仍未知。

## 9. 后续极简页面

菜谱目录第一轮审核完成后，才进入页面实现。页面不调用 DeepSeek，不经过 Planner，不读取用户食材，也不构建自由组合。

```text
打开页面
→ 点击“给我一道一锅出”
→ 从 preview_ready 菜谱中确定性抽取一道
→ 展示固定菜谱与真实出处
→ 点击“换一道”获得另一道
```

同一会话内先遍历未展示菜谱，全部展示过后才允许重新开始。目录为空或菜谱校验失败时显示维护提示，不回退旧 Planner、Legacy API 或自由生成。

## 10. 明确删除或冻结的能力

用户页面不再暴露：

- 食材输入与常用食材 chip；
- 份数选择；
- 忌口输入；
- recommend/pantry 模式；
- normal/quick/fresh/batch intent；
- 多锅规划；
- 食材覆盖评分；
- template 组合；
- DeepSeek 生成；
- AI 营养估算；
- 账号、画像、追踪、收藏和历史。

旧代码可以暂时保留在非公开路径供回溯，但构建门必须证明公开页面无法进入这些能力。确认新路径稳定后再单独决定是否删除旧代码，不在本轮顺手大重构。

## 11. 测试与发布门

### 11.1 目录门禁

公开候选必须满足：

- 菜名有独立外部来源；
- 来源 URL 为 HTTPS 且不是项目自身域名；
- 来源声明字段齐全；
- 固定批量、液体、流程和安全端点完整；
- 菜名、食材、步骤和来源 claim 一致；
- Ratio DSL 可执行且不读取自然语言猜数；
- 营养结构为 A 或 B；
- 状态至少为 `preview_ready`。

### 11.2 页面门禁

- 首屏没有任何输入框、食材 chip、模式或份数控件；
- 首屏只有一个主要动作；
- 点击一次立即显示一份完整固定菜谱；
- 不发起 DeepSeek 或其他付费模型请求；
- `换一道` 不重复当前菜，候选耗尽时明确说明；
- 每道菜显示真实出处；
- 不存在自由拼接菜名；
- 旧 Planner、Legacy 和 ingredient matching 不能从公开页面触发。

### 11.3 发布边界

- 全部实现先写失败测试；
- 提交或部署前运行现有全部测试、菜谱检查、Python 语法检查和构建一致性检查；
- 只更新 Draft PR #1 与 `recipe-validation` Preview；
- 不合并 PR，不部署 production；
- production 必须等待用户审阅目录与 Preview 后单独批准。

## 12. 实施顺序

1. 审计当前 `rice-meal-catalog`，将项目原创自由组合与独立出处菜谱分开；
2. 建立新的来源型权威目录与 validator；
3. 按地域框架系统收集候选，记录来源和空白；
4. 对候选逐道闭合用量、液体、流程、时间与安全事实；
5. 生成人类可读总表，由用户审阅菜名与地域框架；
6. 仅将 `preview_ready` 条目接入极简页面；
7. 运行全量门禁和真实浏览器旅程；
8. 更新 Draft PR 与 Preview，production 保持冻结。

第一阶段的完成标准不是某个任意菜谱数量，而是：地域框架已逐区检索、所有发现项已记账、每个公开候选都有独立出处和可执行合同、未闭合项被诚实阻断。
