# 一锅出真实菜谱优先与受控组合混合推荐设计

日期：2026-07-30

状态：架构方向已确认，待用户审阅本规格

适用范围：Draft PR #1；本规格不授权部署 Preview、production、合并 PR 或继续 5 人 Pilot

## 1. 纠偏原因

当前 Pantry Planner V2 把“覆盖更多用户食材”作为主要工程目标，但运行时并未真正选择 named recipe：

- 候选由 ingredient taxonomy、generic template 与 Ratio DSL 产生；
- 菜名由用户食材名称与 template 后缀拼接；
- 步骤来自全局 action phrase，不直接执行某道 recipe 的专属技法；
- `evidence_recipe_ids` 证明 template 的设计依据，不代表运行时命中了对应菜谱；
- 地域菜单映射账本不参与运行时选择。

结果是页面可能把“上海奉贤咸肉菜饭”表达成“大米、咸五花肉、小白菜家常焖饭”，把“新疆羊肉抓饭”表达成“大米、羊腿肉、胡萝卜、洋葱咸香一锅饭”。更严重时，通用肉类预处理还会要求把“猪肉末切成薄片”。

这不是文案润色问题，而是 recipe identity、组合规划与表达层权责错误：系统证明了食材“可以进入槽位”，却没有证明它们形成一道真实、好吃、技法正确的菜。

## 2. 第一性原理与产品承诺

用户选择食材的含义是：

> 这些食材我希望优先使用；请给我一顿真正合理、能做、愿意吃的饭，不要静默忽略，也不要为了全用而硬凑。

优先级固定为：

1. 过敏、食品安全、食材身份与熟制正确；
2. 组合、口味、质地与技法合理；
3. 达到本次最低食材覆盖承诺；
4. 通过最低门槛后，优先真实 named recipe；
5. 再比较实际覆盖数量、额外主料、时间、步骤负担、多样性与历史。

覆盖不能越过安全和口味，但低覆盖也不能伪装成成功。每项输入必须显示为“已用 / 未用 / 未识别”，并给出具体原因。

### 2.1 直接推荐覆盖门槛

| 去重输入数 N | 目标 | 最低可展示 | 低于门槛 |
|---:|---:|---:|---|
| 1 | 1/1 | 1/1 | 不出候选 |
| 2 | 2/2 | 2/2 | 不允许只用一种 |
| 3 | 3/3 | 2/3 | 不允许只用一种 |
| 4 | 4/4 | 3/4 | 明示未用项 |
| 5 | 5/5 | 4/5 | 明示未用项 |
| 6 | 5/6 | 4/6 | 明示未用项 |
| 7–10 | 先选最合理的 3–5 种 | 至少 4 种 | 引导用户选择本顿优先食材或改为分顿计划 |

用户输入 7–10 种时，不再用单个百分比暗示这些食材适合一锅。页面应先解释“一顿饭通常不宜硬塞全部食材”，再让用户确认本顿最想优先的 3–5 种；未来清库存模式可以另行提供分顿计划。

没有食材数量输入时，只能承诺“安排了多少种”，不能承诺“用完库存”。

## 3. 现状审计基线

首页 16 个常用食材均能被 taxonomy 正确认识，常见输入的主要问题不是身份识别，而是 recipe 密度、template 槽位边界和真实性证据不足。

按现有 72 道 recipe 的核心食材做语义匹配：

- 2 项输入全部命中某一道 recipe：37.5%；
- 3 项全部命中：5.0%；
- 4 项全部命中：0.2%；
- 5–6 项全部命中接近 0。

按当前 generic Planner 纯函数枚举首页常用食材：

- 2 项全用：84.2%；
- 3 项全用：57.1%，至少 2/3：98.8%；
- 4 项全用：30.6%，至少 3/4：89.6%；
- 5 项全用：9.1%，至少 3/5：98.3%；
- 6 项全用：0.6%，至少 4/6：88.7%。

这些数字证明两件事：固定 72 道菜太稀；generic template 可以扩大组合空间，但覆盖率本身不能证明菜式真实或口味合理。

现有 72 道菜单能力审计中，只有 12 道为“单锅且 evidence 对齐”；26 道只是食材槽位兼容，21 道仍有 taxonomy gap，6 道有 planner/template gap，4 道没有核心食材可识别。当前“30/30 浏览器旅程通过”只证明页面与确定性合同稳定，不证明真实菜谱、味道或实际下厨结果。

## 4. 被拒绝的单一路线

### 4.1 只扩固定菜谱

优点是真实菜名、来源与技法容易建立信任。缺点是组合爆炸：即使扩到 150–200 道，也只能明显改善常见组合，不能覆盖家庭输入长尾；若 Planner 仍不消费 recipe identity，单纯扩库对当前确定性候选覆盖几乎没有作用。

结论：扩 recipe 是必要工作，但不能只增加平铺菜谱数量，也不能继续让 recipe 只充当静态 evidence。

### 4.2 只增强模板自由组合

优点是覆盖高、速度快、克数和安全可确定。缺点是“能一起熟”不等于“味道合理”，更不等于“某道真实地方菜”。继续泛化 template 会扩大拼装饭、机械菜名和食材形态错误。

结论：generic template 只能做受控自定义兜底，不能继续作为唯一主线。

### 4.3 选定：真实菜谱优先 + 受控变体 + 自定义兜底

系统同时保留真实菜谱的信任与 template 的长尾覆盖，但两者必须有明确身份边界，不能互相冒充。

## 5. 三层候选模型

### 5.1 Canonical named recipe

只有同时满足以下条件，才允许显示正式菜名：

- recipe 已通过运行时身份审核；
- 用户食材满足 `identity_signature` 的必需食材、状态、部位和形态；
- 关键技法、调味结构、比例与器具边界可完整执行；
- 所有替换均为明确批准且保持菜式身份的 substitution；
- 没有为了提高覆盖吸收会破坏菜式身份的额外食材；
- 页面可展示来源、身份说明与必要署名。

示例：大米、咸五花肉、小白菜满足审核后的签名时，可以显示“上海奉贤咸肉菜饭”。

### 5.2 Approved variant / style adaptation

允许两级变化：

- `approved_variant`：替换仍保持身份，例如经过审核的小白菜 → 菜心，显示“上海咸肉菜饭（菜心版）”；
- `style_adaptation`：关键风味与技法保留，但不再等同原菜，只能显示预审名称，例如“上海菜饭风味家庭版”。

每个 substitution 必须声明身份影响：

- `preserves_identity`
- `named_variant`
- `style_adaptation`
- `breaks_identity`

`breaks_identity` 不得使用原菜正式名称。

### 5.3 Custom combination

没有 named recipe 命中，但受控规则能够证明组合、顺序、比例与安全合理时，可以返回自定义方案：

```text
自定义一锅方案
番茄鸡蛋豆腐烩饭
用上 3/4 种 · 技法参考家常烩饭
```

自定义名称只使用 1–2 个决定性食材与真实技法/成品形态，不罗列全部食材，不使用“正宗、传统、经典、地域名”等身份词。

## 6. Recipe 运行时机器结构

现有 recipe 的 `name / summary / technique / ratio_rules / safety_rules` 不足以确定性执行 named dish。运行时 named recipe 至少补齐：

```json
{
  "recipe_id": "shanghai-salted-pork-vegetable-rice",
  "runtime_identity_status": "approved",
  "identity_signature": {
    "required_ingredients": [],
    "required_states_or_cuts": [],
    "identity_critical_techniques": [],
    "required_equipment": [],
    "forbidden_additions": []
  },
  "approved_variants": [],
  "technique_graph": [],
  "recipe_ratio_rule_ids": [],
  "seasoning_profile_id": "...",
  "safety_endpoints": [],
  "naming_policy": {},
  "source_claims": []
}
```

`auto_approved` 只表示自动闸门通过，不能自动获得 `runtime_identity_status:"approved"`。菜式身份必须独立人工审核。

## 7. 运行时流程

```text
用户食材
→ taxonomy 归一化与忌口检查
→ named recipe matcher
   → canonical / approved_variant / style_adaptation 候选
→ generic template planner
   → 只产生 custom 候选
→ 统一安全、覆盖和额外主料门禁
→ 候选仲裁与多样性选择
→ recipe 专属执行编译器或 generic 执行编译器
→ 确定性成品与契约校验
```

输出至少包含：

- `plan_source: named_recipe | recipe_variant | custom_template`
- `recipe_id` / `variant_id`，custom 时为 `null`
- `identity_level`
- `match_trace`
- `planned_prefer_use` / `unused_prefer_use`
- technique、ratio、seasoning 与 safety 的字段来源

DeepSeek 不得决定菜式身份、食材、替换、技法、调味、克数、液体或安全规则。第一阶段继续使用确定性表达。

## 8. 候选排序与展示

先执行安全、味觉兼容与最低覆盖硬门。未达门槛的候选直接淘汰，不得靠真实菜名获得豁免。所有通过硬门的候选再按以下顺序排序：

1. named identity 等级：canonical > approved variant > style adaptation > custom；
2. 实际使用的用户食材数量与覆盖率更高；
3. 额外主要食材更少；
4. 更符合 intent；
5. 操作与时间负担更低；
6. 更早历史软降权；
7. 稳定 ID。

本规格采用 A 规则：真实菜谱达到最低覆盖门槛时，优先于覆盖更高一档的 custom 候选，但候选卡必须同时展示具体 `x/N`，用户仍能主动选择覆盖更高的自定义方案。这里的“真实菜优先”只发生在候选均已通过相同最低产品承诺之后，不能掩盖低覆盖。

例：真实菜谱用 3/4、自定义方案用 4/4：

1. 经典菜谱：上海咸肉菜饭 · 用 3/4；
2. 自定义方案：咸肉香菇青菜焖饭 · 用 4/4；
3. 另一道真实菜谱或身份明确的变体；没有可靠第三张则不凑数。

不同候选必须至少在 recipe identity、template、关键技法或使用食材集合上存在真实差异，不能只换菜名。

## 9. 扩库策略

第一优先级不是立刻增加菜谱总数，而是让已有真实菜谱进入运行时，并补齐可执行的菜式身份；完成这条主链后，再按真实组合缺口扩充数量。指标从“菜谱总数”改为“可运行真实菜式能力”：

1. 先把已有 72 道中的高价值中国菜谱补成可执行 named recipe，而不是立即增加总数；
2. 首批选择 6 道身份差异明显的现有菜进行机器化试点：上海奉贤咸肉菜饭、新疆羊肉抓饭、北方豆角焖面、广式腊味煲仔饭、泉州浥饭、高丽菜香菇炊饭；
3. 每道完成身份、技法、调味、比例、变体、来源和实际试做审核后才进入 Preview；
4. 再沿已建立的中国地域框架逐批扩展，优先补真实用户输入的组合缺口；
5. 新增数量不是验收条件。验收看 clean match 覆盖、身份准确率、实际做饭成功率和第二天复用。

未来 150–200 道扩展仍须遵守现有 Phase A exit gate，不因本规格自动放行。

## 10. 错误与诚实出口

- 输入 2 种却没有可靠 2/2：不展示 1/2 候选；说明这两种暂时没有可靠同锅做法。
- 输入 3–6 种低于最低门槛：展示哪些组合被拒绝以及原因，允许用户明确指定本顿最优先食材。
- named recipe 缺少身份关键食材：降级 custom，不使用原菜名。
- named recipe 执行图、比例或调味资料不完整：fail closed，不用 generic 规则静默补齐后继续挂原名。
- custom 只有“槽位兼容”而没有 affinity/味觉依据：不得展示。
- 未识别、忌口或形态不兼容：逐项解释，不静默丢弃。

## 11. 测试矩阵

### 11.1 真实菜式身份

- 上海咸肉菜饭完整核心：正式菜名、咸肉与米起香、125–140g 液体区间、叶菜后放、条件性不补盐。
- 上海菜饭缺咸肉或叶菜：禁止显示正式名称。
- 新疆抓饭完整核心：羊肉 → 洋葱胡萝卜 → 量可用余液 → 加米。
- 新疆抓饭缺胡萝卜或洋葱：降级 custom。
- 北方豆角焖面：豆角和蛋白先熟、鲜面分段补液；猪肉末不得出现“切薄片”。
- 广式煲仔饭、泉州油饭与高丽菜炊饭不得共享一套无差别步骤或比例。

### 11.2 覆盖承诺

- 2 项输入不得展示 1/2。
- 3 项优先 3/3，允许 2/3，禁止 1/3。
- 4 项最低 3/4；5 项最低 4/5；6 项最低 4/6。
- 10 项不得暗示适合全塞一锅；必须出现优先食材或分顿入口。
- 每张卡和成品的已用、未用、额外主料完全一致。

### 11.3 仲裁与命名

- named 3/4 与 custom 4/4 同时存在时，named 第一、custom 第二，覆盖数字清晰。
- 自定义方案不得出现地域、正宗、经典、传统词。
- approved variant 显示具体替换；breaks identity 必须降级 custom。
- 三张候选必须存在结构差异，不按数量凑满。

### 11.4 安全与确定性

- 过敏、部位、生熟、形态、克数、液体和安全终点全部由服务端重算。
- 客户端不能伪造 `recipe_id` 或 `identity_level`。
- named recipe 缺失专属规则时 fail closed。
- 完整旅程 0 次 DeepSeek 调用；失败不自动重试。

### 11.5 真人下厨门

浏览器点击门只能证明交互稳定。每个进入 Preview 的 named recipe 至少完成一次家庭试做记录；首批 6 道完成后，再进行 5 人 Pilot。Pilot 继续记录实际做完、卡点、味道、步骤可理解性和第二天复用，不用点击冒充结果。

## 12. 分阶段迁移

1. **暂停当前 Pilot**：保留 Preview 供内部诊断，不再把 30/30 浏览器门称为产品完成。
2. **Shadow named matcher**：不改变页面，针对已有 72 道记录 exact/variant/broken/no-match 和误匹配。
3. **首批 6 道 named compiler**：补机器化身份和专属执行图，TDD 验证真实名称、技法、比例与调味。
4. **Hybrid candidate UI**：接入三类候选和 A 排序，移除食材长串拼接菜名。
5. **Custom affinity 门**：只保留有味觉与质地依据的 template 组合。
6. **真实浏览器与家庭试做**：先跑工程门，再恢复 5 人 Pilot。
7. **按真实缺口扩地域菜谱**：每批独立评审，不盲目冲数量。

## 13. 非目标与冻结边界

本轮不增加账号、用户画像、营养追踪、云端用户行为画像、多 Agent 运行时、自由 LLM 组合或 production 部署。

不删除 generic Planner、Ratio DSL 或 LLM 回滚代码；只重新划分其职责。现有营养红线、来源红线、Phase A 闸门、过敏与熟制契约全部继续有效。

在用户审阅本规格并确认前，不修改运行时代码、不新增 recipe、不部署 Preview 或 production。
