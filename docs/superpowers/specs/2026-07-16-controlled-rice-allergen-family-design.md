# Controlled Rice Allergen Family Design

Date: 2026-07-16
Status: Approved in conversation; awaiting written-spec review

## Context

The targeted six-case live gate exposed a serious allergen leak. The request contained `大米过敏`, recipe selection correctly rejected rice-based candidates, but the generated fallback meal added and served `米饭（即食）`. The deterministic validator returned no allergen flag.

The existing allergen check has two boundaries that explain the leak:

1. it compares only `ingredients[].name` against canonical dislikes;
2. the recipe alias table maps `白米` to `大米`, but does not treat prepared rice forms such as `米饭（即食）` as the same allergen family.

The prompt already warns that rice allergy must exclude rice wording from all model fields. Prompt guidance alone is not a release gate.

## Goal

Deterministically reject a generated meal when a user declares a rice allergy and any user-facing recipe field contains a controlled rice-food form, while avoiding broad substring matching that would incorrectly block millet, corn, or unrelated words.

## Non-goals

- Do not build a universal food-allergen ontology in this task.
- Do not infer medical severity or provide medical advice.
- Do not automatically remove, replace, or rewrite an allergenic food.
- Do not change recipe selection, approved source metadata, nutrition rows, grams, or nutrition values.
- Do not treat every word containing `米` as rice.
- Do not automatically include fermented rice-derived condiments such as rice vinegar or rice wine in this first controlled family.
- Do not address numeric water totals, dish-form validation, serving structure, or hidden second heating in this task.

## Approaches considered

### Controlled rice family across selected fields — selected

Create a finite rice-food family and scan only user-facing generated content. This directly covers the observed leak while preserving explainable boundaries and Worker/Python parity.

Benefits:

- deterministic;
- narrow enough to test exhaustively;
- catches leaks outside the ingredient list;
- avoids inventing replacements or quantities.

Trade-off: other allergen families still need separate reviewed rules later.

### Prompt-only reinforcement — rejected

The existing final preflight already gives `米过敏时不得写“配米饭”` as an example, yet the live response still served instant rice.

### Whole-JSON fuzzy substring scan — rejected

Searching serialized JSON for `米` would create false positives from `小米`, `玉米`, `薏米`, server metadata, source titles, and messages that explicitly say a food was not used.

## Controlled rice-food family

The first family recognizes explicit food forms derived from rice:

- raw or staple forms: `大米`, `白米`, `糙米`, `糯米`, `粳米`, `籼米`, `黑米`, `紫米`, `红米`;
- cooked forms: `米饭`, `白米饭`, `糙米饭`, `糯米饭`, `黑米饭`, `紫米饭`, `剩米饭`, `隔夜米饭`, `即食米饭`;
- porridge forms: `白粥`, `米粥`, `大米粥`, `糙米粥`;
- flour, drink, noodle, and sheet forms: `米粉`, `糙米粉`, `米浆`, `米糊`, `米线`, `河粉`, `米皮`;
- other clear rice staples: `年糕`, `糍粑`, `饭团`.
- explicit rice-dish forms: `焖饭`, `炒饭`, `烩饭`, `泡饭`, `汤饭`, `菜饭`, `煲仔饭`, `盖浇饭`, `咖喱饭`, `丼饭`, `香料饭`, `番茄饭`.

Benign preparation/state wording surrounding one of these forms remains part of the same match, for example `米饭（即食）`, `熟米饭`, or `剩余米饭`.

The family deliberately excludes:

- `小米`, `玉米`, `薏米`, `高粱米`;
- `小米椒`, `糯米椒`, and other produce names that merely contain a rice token;
- `米醋`, `米酒`, `料酒`;
- words where `米` is not a rice-food reference;
- generic `饭` without a controlled compound.

## Fields in scope

Scan only generated, user-facing recipe content:

- `dish_name`;
- every `ingredients[].name`;
- every `steps[]` string;
- `note`;
- `taste_preview`;
- `form`;
- `why`;
- every `flavor_tags[]` string.

Do not scan:

- `unused_pantry`;
- `used_pantry`;
- `pairing_basis`;
- `source_refs`;
- `safety_checks`;
- `validation_flags`;
- model usage, intelligence, or server diagnostics.

`pairing_basis` is excluded because it is generated by the server from trusted selection metadata, not by the model, and can legitimately describe why a rice candidate was rejected or which non-allergenic base was selected. The user-facing model content remains the hard boundary for this task.

## Detection and flag behavior

1. Normalize each dislike through the existing constraint sanitizer.
2. Activate the controlled rice-allergen family only when the normalized dislike clearly names common rice or cooked rice, including `大米过敏`, `白米过敏`, `米饭过敏`, or an existing alias resolving to `大米`.
3. Extract bounded user-facing strings from the meal without serializing arbitrary objects.
4. Search those strings for controlled rice-food tokens using longest-token-first matching and explicit compound exclusions.
5. Process fields in the fixed order listed above and emit one stable flag per distinct matched display form, preserving the first occurrence. For an ingredient-name match, preserve the complete ingredient name such as `米饭（即食）`; for free-text fields, use the controlled matched token such as `白米饭` or `河粉`:

   `allergen_present:<matched form>`

6. Preserve the existing ingredient allergen check for all other dislikes.
7. Never clear or replace another validation flag.

Examples:

- `ingredients: [{name: "米饭（即食）"}]` with `大米过敏` → `allergen_present:米饭（即食）`;
- `steps: ["最后配一碗白米饭"]` with `大米过敏` → `allergen_present:白米饭`;
- `dish_name: "鸡肉河粉"` with `大米过敏` → `allergen_present:河粉`;
- `steps: ["加入玉米粒"]` with `大米过敏` → no rice-allergen flag;
- `steps: ["加入糯米椒"]` with `大米过敏` → no rice-allergen flag;
- `note: "不使用米饭"` still contains a prohibited served-food reference only if the meal otherwise instructs serving it. Pure negated safety wording should not create a flag.

To keep negation behavior bounded, the validator ignores a controlled token when its immediate action window is clearly exclusionary, such as `不使用`, `不含`, `不要`, `不放`, `不加`, `无需`, `避免`, or `去掉`. It does not treat `未用库存: 大米` metadata as model content because that field is out of scope.

## Data flow

1. DeepSeek returns the meal JSON.
2. Existing normalization and deterministic high-risk safety repair run unchanged.
3. Existing ingredient/step, controlled-consumable, allergen, one-pot, and anchor validation runs.
4. The controlled rice-family validator scans the selected model-facing fields.
5. Any rice-family leak becomes a hard `validation_flag`.
6. The existing frontend retry/fallback path rejects the flagged response.

No ingredient, step, gram, nutrition, or source field is mutated.

## Worker and Python parity

`worker/src/worker.js` remains authoritative. Python must mirror:

- family activation;
- field extraction;
- token order;
- exclusion and negation rules;
- emitted flag text and ordering;
- malformed-value handling.

Parity tests compare the complete flag arrays, not just the presence of one rice flag.

## Required tests

### Reproduce the live defect

With `dislikes: ["大米过敏"]`, a meal containing `米饭（即食）` in ingredients and instructions must emit an allergen flag.

### Field coverage

Place one controlled rice form separately in:

- dish name;
- ingredient name;
- step;
- note;
- taste preview;
- form;
- why;
- flavor tag.

Each must be rejected when the rice family is active.

### Positive family forms

Cover at least:

- `大米`, `白米`, `糙米`, `糯米`;
- `米饭（即食）`, `剩米饭`, `白米饭`;
- `白粥`, `米粥`;
- `米粉`, `米线`, `河粉`, `米皮`;
- `年糕`, `糍粑`, `饭团`.
- common rice-dish forms such as `焖饭`, `炒饭`, `盖浇饭`, and `咖喱饭`.

### False-positive controls

Do not reject:

- `小米`, `玉米`, `玉米粒`, `薏米`;
- `小米椒`, `糯米椒`;
- `米醋`, `米酒`, `料酒`;
- generic `饭` without a controlled rice compound;
- source titles, unused-pantry metadata, or server pairing metadata;
- explicit exclusion wording such as `不含米饭` when no other field contains rice food.

### Activation controls

- `大米过敏`, `白米过敏`, and `米饭过敏` activate the family.
- An unrelated allergy does not activate the rice family.
- Malformed values do not throw.
- Duplicate mentions produce one stable flag per matched normalized form.

### Integration and regression

- A generation containing the live defect is a hard failure through the existing frontend retry path.
- Worker and Python produce identical arrays.
- Existing 126 tests, food check, recipe check, 100-case regression, syntax checks, and `git diff --check` remain green.

## Acceptance and release sequence

1. Worker and Python reproduce and block the preserved live rice-allergy leak.
2. All bounded positive and negative cases pass.
3. All offline gates pass without nutrition, source, recipe-selection, or safety-tail regression.
4. Run a minimal no-retry live allergen sample on an owned port. This sample must include the preserved `大米过敏` request and may include at most two additional bounded allergy variants.
5. If any allergen leak or false positive remains, the 30-case, mobile, preview, and production gates stay blocked.
6. Even if the minimal live sample passes, production remains blocked by the other known strict semantic defects and the Phase A exit conditions.
