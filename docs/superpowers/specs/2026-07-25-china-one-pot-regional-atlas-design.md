# 中国一锅主餐地域地图与渐进扩库设计

日期：2026-07-25

状态：已由 `2026-07-26-national-regional-menu-atlas-v2-design.md` 扩展替代；本文件保留为第一版决策记录

适用范围：Draft PR #1 后续规划；本规格本身不授权新增生产 recipe、部署 Preview、部署 production 或合并 PR

## 1. 背景

一锅出当前有 72 道 recipe，并已建立 Pantry Planner V2、ingredient taxonomy、template catalog 与 Ratio DSL。现有 recipe 在江南菜饭、南京菜饭、福建咸饭、广东煲仔饭、新疆抓饭以及常见家常食材组合上已有基础，但地域分布不均：东北、山东、中原、川渝与云贵等区域的一锅主餐原型明显不足。

用户提出的正确方向不是立即把 72 道扩成几百道，而是先建立一个全国性框架：明确要研究哪些地域、城市、民族地区和一锅技法，逐步补充原型、变种、来源和家庭适配方案。

本设计将该框架命名为“**中国一锅主餐地域地图**”。它是研究、规划与产品决策资产，不是另一份固定菜谱清单。

## 2. 第一性原理目标

“一锅出”是家庭结果概念，不是器具教条。

一个方案的目标是：

- 用一口主要锅具或一个主要烹饪设备完成；
- 减少洗切、看火、转锅和收拾负担；
- 形成一顿完整、合理、好吃的家庭主餐；
- 尽可能消化用户已有食材，但不强行组合不合适的食材；
- 让普通家庭使用常见设备、常见食材和可接受时间完成；
- 对地域原型、家庭改造和来源保持诚实。

因此，传统做法不要求原样复刻。只要不破坏核心味型、搭配逻辑和安全边界，可以进行家庭化改造。

## 3. 非目标

本阶段不做：

- 立即批量新增生产 recipe；
- 按省份平均分配菜谱数量；
- 为追求地域数量收录低频、难买、难操作且无家庭价值的菜；
- 把所有地方菜强行改成一锅；
- 把地域原型直接变成 template；
- 新建完整中国饮食知识图谱；
- 让 DeepSeek 自由创造地域归属、核心食材或传统技法；
- 复制 RecipeDB、商业菜谱网站或许可不明内容的完整步骤与图片；
- 新增账号、用户画像、营养追踪、多 Agent 或生产部署。

## 4. 三层资产结构

### 4.1 Atlas entry：地域地图节点

Atlas entry 记录一个地方原型或地方技法家族。它回答：

- 哪里有这种做法；
- 当地通常使用什么主食、味型和核心技法；
- 哪些部分是传统事实；
- 哪些部分可以进行家庭一锅适配；
- 它能解决哪些真实冰箱食材需求。

地图节点不自动进入生产，也不直接展示为生成结果。

### 4.2 Recipe：技法与证据资产

现有及未来通过闸门的 recipe 提供：

- 技法依据；
- 比例与液体依据；
- 熟制与安全依据；
- 来源与地域证据；
- 对 Planner 输出的 grounding。

Recipe 不决定全部组合空间，也不要求每个地图变种都变成一条固定 recipe。

### 4.3 Template + taxonomy：组合能力

真正决定用户食材如何组合的是：

- template rules；
- ingredient taxonomy；
- Ratio DSL；
- compatibility / incompatibility rules；
- shape、cook speed、moisture、texture 与 cooking risk。

地域研究若发现新的稳定组合规律，应先判断它属于：

1. 现有 template 已能表达，仅需增加 evidence；
2. taxonomy 或 compatibility 需要校准；
3. Ratio DSL 需要增加机器规则；
4. 确实出现新的通用技法结构，才提出 template 变更；
5. 只适合文化内容，不适合进入产品。

禁止通过不断增加固定 recipe 来代替组合能力建设。

## 5. 收录边界

### 5.1 A 类：天然一锅

传统原型本身就在同一锅或同一主要器具中完成主食和主要配菜，例如：

- 菜饭、咸饭、焖饭、抓饭；
- 焖面、烀面；
- 铁锅炖配锅边饼、花卷或粘卷子；
- 煲仔饭、砂锅饭；
- 社饭、油饭等饭菜合一主食。

### 5.2 B 类：家庭一锅适配

传统版本可能有预炒、另蒸、特殊器具或较长准备，但在不破坏身份的前提下可以改为：

- 同锅分阶段下料；
- 砂锅、柴火锅或铜锅改为电饭煲、普通锅或压力锅；
- 大块慢炖部位改为适合家庭时间的合法部位；
- 地方难买食材使用明确 substitution；
- 节庆大份量缩为 2–4 人份；
- 菜与主食原来分开，但味型和技法允许时合并成焖饭、汤饭、焖面或锅边主食。

B 类必须明确标记 `adaptation_type` 和 `adaptation_notes`，不得对外宣称为传统原做法。

### 5.3 排除条件

出现以下任一情况时，不进入产品候选：

- 只能靠强行拼接用户食材成立；
- 家庭化后失去原型的核心味型或技法身份；
- 需要多个关键锅具且无法合理合并；
- 依赖难以控制的发酵、生食或高风险熟制条件；
- 无法建立水量、比例、时间或安全边界；
- 只能消耗一种低价值食材，不能改善产品覆盖；
- 来源只能证明菜名，不能证明核心食材或高层技法。

## 7. 一锅技法家族

地图的第二主轴不是省份，而是跨地域技法：

| family_id | 技法家族 | 主食状态 | 组合价值 |
|---|---|---|---|
| raw-rice-braise | 生米同焖 | 生米 | 菜饭、咸饭、焖饭、抓饭 |
| cooked-rice-stir | 熟饭翻炒 | 剩米饭 | 炒饭和快速清库存 |
| cooked-rice-stew | 熟饭烩煮 | 剩米饭 | 烩饭、汤饭、粥饭 |
| noodle-braise | 面菜同焖 | 生面或半熟面 | 焖面、烀面、部分蒸面适配 |
| noodle-broth | 汤面一锅 | 生面、面片或米粉 | 烩面、卤面、面片锅 |
| stew-with-staple | 炖菜带主食 | 饼、卷子、花卷等 | 东北铁锅炖、锅边主食 |
| claypot-rice | 砂锅主食 | 生米 | 煲仔饭、砂锅饭 |
| glutinous-mixed-rice | 糯米杂粮同锅 | 糯米或混合米 | 油饭、社饭、民族饭 |
| vessel-adapted-rice | 特殊容器家庭化 | 生米或糯米 | 铜锅、竹筒、菠萝容器路线 |

同一个地域可以有多个 family；同一个 family 可以跨多个地域。这样既保留地方故事，也避免模板退化成固定菜名。

## 8. 地图节点机器字段

第一版建议使用结构化 JSON 或 YAML，字段至少包括：

```json
{

  "region_path": ["东北", "黑龙江"],
  "locality": ["待进一步核实城市或县域"],
  "prototype_name": "铁锅炖配锅边主食",
  "aliases": [],
  "family_id": "stew-with-staple",
  "inclusion_class": "natural_one_pot",
  "adaptation_type": "home_equipment_and_portion",
  "adaptation_notes": [],
  "core_flavor": ["咸鲜", "酱香"],
  "staple_state": ["corn_dough", "wheat_dough"],
  "core_slots": ["protein", "stew_vegetable", "staple"],
  "optional_slots": ["mushroom", "tofu"],
  "incompatible_rules": [],
  "shape_or_cut_requirements": [],
  "cooking_order_summary": [],
  "ratio_evidence_status": "unresearched",
  "safety_evidence_status": "unresearched",
  "pantry_gap_items": ["鸡肉", "排骨", "豆角", "土豆", "白菜", "菌菇"],
  "source_refs": [],
  "source_confidence": "discovery_only",
  "product_destination": "undecided",
  "status": "research_queue",
  "priority_score": null
}
```

重要区分：

- `prototype_name` 是研究对象，不是最终菜名；
- `source_refs` 证明地方事实，不等于授权复制完整做法；
- `product_destination` 可为 `recipe_evidence | taxonomy_rule | template_evidence | content_only | rejected`；
- 只有通过研究与质量闸门后，才能决定是否修改生产资产。

## 9. 70/30 优先级模型

首批排序采用 100 分制。

### 9.1 产品需求：70 分

- 高频 pantry 食材缺口：0–30 分；
- 能否一次合理覆盖 2–4 种常见食材：0–20 分；
- 家庭操作负担与常见设备适配：0–10 分；
- 是否能形成多个真实有效 plan，而不是只增加菜名：0–10 分。

### 9.2 地域与内容价值：30 分

- 当前地域空白程度：0–10 分；
- 地方代表性与来源可核实性：0–10 分；
- 是否能形成清晰的地域故事和变种关系：0–10 分。

### 9.3 风险扣分

以下风险从总分中扣除，最高扣 30 分：

- 难以建立水量或时间规则；
- 特殊食材难以家庭替换；
- 高风险熟制或预处理复杂；
- 家庭化会明显损害传统身份；
- 与现有家族高度重复，仅增加同构固定菜谱。

分数只用于研究排序，不代表自动批准。

## 11. 来源策略

### 11.1 来源优先级

1. 地方政府、地方志、文旅部门、非遗与公开地方标准；
2. 权威媒体、博物馆、研究论文及正式出版物的可核实介绍；
3. 许可清楚的开源或公共领域资料，用于技法发现；
4. 公开社交内容只用于发现候选和常见变种，不单独作为批准依据。

### 11.2 来源证明范围

地域来源主要证明：

- 菜名或技法确实存在；
- 地域或族群关联；
- 核心食材；
- 高层烹饪方法；
- 传统变种边界。

生产比例、家庭设备适配、份量和安全步骤必须独立结构化与验证。

### 11.3 许可边界

- RecipeDB 只用于研究发现，不进入生产数据或生成请求；
- GitHub 项目代码许可不自动覆盖其中汇总的第三方菜谱；
- 不复制来源原文、完整步骤或图片；
- `approved` recipe 继续遵守项目现有来源五要素与署名规则；
- `auto_approved` 不得对外宣称人工批准。

## 12. 研究到产品的闸门

每个研究题目依次经过：

```text
发现候选
→ 核实地域、名称、核心食材和高层技法
→ 归入技法家族并识别变种关系
→ 评估家庭一锅适配价值
→ 提取槽位、形态、兼容和不兼容规则
→ 建立 Ratio DSL 与液体、时间、安全证据
→ 确定 product_destination
→ 进入 Preview 资产
→ 运行真实多食材旅程与人工厨房评审
→ 用户批准后才允许生产晋升
```

硬闸门：

- 不得强行覆盖互不相容的 must_use 食材；
- 食材形态必须适配做法，例如牛里脊不能被当作牛腩长炖；
- 禽肉、猪肉、海鲜、鸡蛋必须有明确熟制终点；
- 生米、熟饭、糯米、面条和面团必须使用各自的比例规则；
- DeepSeek 不得决定新增、删除或替换主要食材；
- 营养数值继续遵守两层权威查表红线；
- 每次晋升前必须运行现有 recipe、planner 和构建门禁。

## 13. 真实产品验证

一个家族进入产品前，不只验证“能返回”，还要验证：

### 13.1 覆盖

- 两种食材应尽量达到 2/2；
- 三种食材优先 3/3，最低合理覆盖 2/3；
- 四至六种 pantry 食材应提供合理单锅或完整多锅计划；
- 不能出现选择 14 种食材却只使用 1–2 种且没有解释的结果。

### 13.2 三方案差异

首屏三个方案不应只是围绕同一种蛋白换菜名。应优先形成可解释梯度，例如：

- 方案一：味型最稳、覆盖较少；
- 方案二：覆盖更多食材；
- 方案三：完整覆盖或明确分锅。

如果不存在三个同等可靠的方案，应诚实减少方案数量，不用低质量方案凑满三张卡。

### 13.3 换一换

- 必须重新运行 planner；
- 新计划至少在 template、slot assignment、锅数或锅序上真实不同；
- 没有第二套同等承诺的计划时返回 `no_alternative_plan`；
- 不允许只改菜名、描述或 DeepSeek 文案。

### 13.4 家庭直觉

人工评审至少回答：

- 用户会觉得这些食材应该放在一起吗；
- 家庭常用锅具能否完成；
- 时间和步骤是否与日常做饭相符；
- 味道是否有明确、熟悉的参照；
- 未使用食材的理由是否合理；
- 是否真的减少了用户决策和操作负担。

点击、换菜或停留不能冒充“真正做了并且好吃”。只有用户确认实际做过的结果才作为产品质量证据。

## 14. 分阶段交付

### 阶段 0：地图底座

- 建立结构化 atlas schema；
- 将现有 72 道 recipe 归入地域和技法家族；
- 标出地域、技法和高频 pantry 食材缺口；
- 不修改生产 recipe。

### 阶段 1：六个首批家族研究

- 对约 24 个研究题目逐条核实；
- 合并同构变种；
- 标注来源、家庭改造和风险；
- 形成 `product_destination` 建议。

### 阶段 2：小批 Preview 接入

- 每次最多接入一个家族；
- 先修改最小必要的 evidence、taxonomy、Ratio DSL 或 template rules；
- 运行自动旅程与人工评审；
- 不因完成研究而自动新增 recipe。

### 阶段 3：按真实缺口继续扩展

- 根据 Preview 中的未覆盖食材、无替代计划和真实做饭反馈选择下一个家族；
- 地图提供长期方向，但实际开发顺序由用户问题决定；
- 每轮继续维持约 70% 产品缺口、30% 地域代表性的优先级。

## 15. 成功标准

地图框架成功不以收集数量衡量，而以以下结果衡量：

- 全国主要地域和一锅技法都有明确位置与研究状态；
- 新候选不再零散加入，而能说明为什么值得研究；
- 同一技法的地域变种能够复用 template 与 Ratio DSL；
- 三方案在覆盖、味型或计划结构上存在真实差异；
- pantry 模式不再以低覆盖固定 recipe 冒充清库存成功；
- 用户实际做饭后认为方案合理、可完成、愿意再次使用；
- 地域内容与产品能力可以互相支撑，但不互相冒充。
