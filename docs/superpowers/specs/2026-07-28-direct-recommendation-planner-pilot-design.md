# 直接推荐 Planner 主线与 Pilot 前硬化设计

- 日期：2026-07-28
- 状态：产品与技术方向已确认，等待规格审阅
- 适用范围：Draft PR / Preview；不授权合并或部署 production
- 第一轮 Pilot：只开放「直接推荐」

## 1. 决策摘要

第一轮 5 人 Pilot 不再让默认用户走旧的固定菜谱选择器，也不开放尚未兑现完整覆盖承诺的「帮我清库存」。默认路径改为：

1. 用户输入这顿饭的偏好食材和 intent；
2. 确定性 Planner 在不调用 DeepSeek 的情况下生成 1–3 个真实有效的候选计划；
3. 用户选择计划；
4. Preview 默认由确定性本地表达器把已锁定计划组装为菜名、理由和自然语言步骤；LLM 表达路径保留为可逆对照，但不参与默认 Pilot；
5. 服务端逐项校验食材、克数、比例和安全终点，不允许模型改变计划。

Pilot 要验证的核心假设不是“系统能生成多少菜名”，而是：用户能否快速得到一份符合家庭直觉的方案，真正做完，并在第二天愿意再次打开。

## 2. 当前问题与证据

### 2.1 默认路径仍是旧选择器

当前默认 `/generate-meal` 路径仍以固定 recipe 候选和 `buildPantryPlan()` 为主。Planner V2 只在本地实验参数中使用，真实用户没有获得确定性规划器的主要价值。

这造成：

- 候选页本身就产生一次慢速、付费且不稳定的模型调用；
- 多食材输入常出现三张卡都只覆盖少量食材；
- 为凑候选数量而展示质量明显较差的卡；
- 候选标题、实际使用食材和最终成品可能不一致；
- 换一换可能等待二十秒后仍失败；
- 固定 recipe 数量继续增加，也无法解决任意家庭组合的覆盖问题。

### 2.2 Planner V2 能力真实存在，但尚未达到切换条件

本地确定性运行已经证明 Planner 可以正确规划部分家庭组合。例如「鸡腿 + 土豆」能进入焖面锅，两项均被使用，只补面条和水，并附有完整禽肉熟制安全终点。

但切换前仍有确定性硬伤：

- 「虾仁」「玉米」等常见首页食材尚未被 taxonomy 识别；
- 同一响应曾同时出现 `plan.coverage_ratio = 1`、`pot.ok = true`、`pot.coverage_ratio = 0`；
- 这说明覆盖语义尚未形成单一、可供前端和测试共同依赖的契约；
- 当前模板深度不足以保证每个组合都有第二套同等承诺的计划。

因此本次切换不是简单接线，必须先完成识别、覆盖语义和计划一致性硬化。

### 2.3 真人点击旅程暴露的典型失败

以下输入必须进入切换前回归集：

- 面条、猪里脊、白菜、香菇、胡萝卜：三张卡均只有 2/5，且没有使用猪肉；选择后还可能触发份量不足。
- 大米、牛里脊、番茄、鸡蛋、西兰花：候选等待约二十秒，最好仅 3/5；换一换再等待后失败。
- 鸡胸肉、土豆、洋葱、胡萝卜、西兰花、玉米、豆腐、鸡蛋：旧多锅页面只覆盖 6/8，第三锅只用一种食材，完成第一锅后没有后续进度。
- 大米、虾仁、白菜、玉米、番茄：可以偶尔得到 5/5 首锅，但没有第二套可靠计划，换一换失败。
- 候选标题曾出现未实际使用的食材，例如标题含「土豆」但 `used_items` 不含土豆。

这些问题共同指向：候选计划必须先由确定性系统成立，模型不能继续承担选组合的职责。

## 3. 范围与非目标

### 3.1 本轮范围

- 补齐第一轮 Pilot 所需的高频食材 taxonomy；
- 统一覆盖率和食材状态语义；
- 将「直接推荐」候选页切到确定性 Planner；
- 将换一换切到 Planner；
- 将表达层收敛为人工受控文案目录和确定性组装器，并继续做零漂移校验；
- 建立 30 条影子对照和 Preview 真人浏览器发布门；
- 通过后开展 5 人 Pilot。

### 3.2 明确不做

- 不部署或修改 production；
- 不合并 Draft PR；
- 不在 Pilot 前增加 recipe，现有 72 道保持不变；
- 不在本轮扩大地域菜、固定菜谱或模板数量；
- 不开放有状态多锅清库存；
- 不增加账号、用户画像、营养追踪、长期行为数据或多 Agent 产品能力；
- 不用点击行为冒充真实做饭结果；
- 不为填满三张卡降低候选质量；
- 不在计划失败时静默回退旧选择器。

## 4. 第一轮产品承诺

### 4.1 只开放「直接推荐」

第一轮 Pilot 的输入食材均视为 `prefer_use`：系统应优先使用，但不承诺全部用完。

页面必须诚实展示：

- `used_items`：本方案会用到的用户食材；
- `unused_items`：本方案暂不使用的用户食材；
- 未使用原因：兼容性、锅容量、时间、形态或当前模板能力限制；
- `required_extra_items`：完成方案需要的允许补充项。

输入非空且至少有一个食材被识别时，正常候选原则上至少使用一个用户食材。

### 4.2 暂不开放「帮我清库存」

清库存的产品承诺是覆盖全部可识别 `must_use` 食材。当前多锅状态机尚未贯通，不能用残缺计划伪装清库存成功。

- 若目标首页从未对用户展示该入口：第一轮直接不显示；
- 若测试版本中已有用户见过入口：置灰并显示「清库存正在做，先来解决今晚吃什么」；
- 不用静态“第二锅建议卡”替代真正的连续计划；
- Pilot D2 回访单独询问清库存需求，不新增遥测。

## 5. 确定性候选计划契约

### 5.1 调用与性能

- 候选页调用 `/plan-meal`；
- `/plan-meal` 调用 DeepSeek 次数必须为 0；
- 规划结果必须可复现；
- Preview 发布门要求规划接口 P95 小于 2 秒；
- 页面展示 1–3 个有效计划，绝不为了视觉数量凑满三张。

### 5.2 覆盖门槛

对去重后的已识别用户食材数 `N`：

| N | 正常候选最低覆盖 |
|---|---|
| 0 | 可做无食材直接推荐 |
| 1 | 1/1 |
| 2 | 2/2 |
| 3 | 至少 2/3，优先 3/3 |
| 4 | 至少 3/4 |
| 5 | 至少 3/5 |
| 6 | 至少 4/6 |
| 7 及以上 | 至少 60%，否则不给正常候选 |

当 `N > 1` 时，不得把只使用一种食材的计划展示成正常候选。

若没有计划达到门槛：

- 不展示低覆盖卡；
- 进入“当前还没有足够可靠的一锅组合”状态；
- 显示系统能识别但没有安排的食材和原因；
- 提供「修改食材」入口；
- 可以明确展示“当前只能可靠使用其中一种”，但不得把它包装成满足多食材需求的正常方案。

### 5.3 候选排序与差异

- 第一张必须是满足约束后的最高覆盖计划；
- 第二、第三张必须在 `template_id`、槽位分配、主食形态或烹饪形态中至少一项不同；
- 后续候选的食材覆盖不得比最佳候选少两项或更多；
- 所有候选均独立对完整 original input 计算覆盖，不能从上一张卡的剩余食材继续扣减；
- 完整覆盖方案存在时必须优先展示；
- 安全、形态和时间硬约束优先于覆盖分。

### 5.4 允许补充项

第一阶段 `required_extra_items` 只能包含：

- 基础主食；
- 水、汤底等基础液体；
- 食用油；
- 基础调味。

不得为了提高表面覆盖或凑成菜，要求用户额外购买肉、蛋、豆腐、蔬菜或菌菇等主要食材。

## 6. 食材身份与覆盖字段

### 6.1 Taxonomy 准入门

默认切换前必须满足：

- 首页所有常用食材 chip 识别率 100%；
- 大米、熟米饭、面条等主食状态可区分；
- Pilot 高频蛋白和蔬菜可识别；
- 明确补齐「虾仁」「玉米」；
- 原始名称、canonical、category、生熟状态、shape/cut、recognized 均保留；
- 未识别食材不得静默丢弃，必须出现在响应解释中。

### 6.2 覆盖字段单一语义

`coverage_ratio` 的分母统一为本次提交的去重用户食材总数。未识别项仍在总分母中，并通过 recognition 字段单独解释。

响应至少返回：

- `coverage_ratio = planned_submitted_items / dedup_submitted_items`；
- `recognition_ratio = recognized_items / dedup_submitted_items`；
- `recognized_coverage_ratio = planned_recognized_items / recognized_items`；
- `planned_prefer_use`；
- `unused_prefer_use`；
- `normalized_items`。

第一轮只启用单锅直接推荐时：

- 顶层 `plan.coverage_ratio` 必须与该 pot 对原始输入计算的 `pot.coverage_ratio` 一致；
- `pot.ok = true` 不得与 `pot.coverage_ratio = 0` 同时出现；
- 前端不得自行重新定义覆盖率。

### 6.3 生熟与部位保护

- 大米不得静默变成熟米饭；
- 剩米饭不得套用生米吸水比例；
- 牛里脊可进入通用牛肉槽，但不能进入明确要求牛腩或牛肉末的规则；
- 食材标题、槽位、克数和安全规则都必须基于同一个 normalized identity。

## 7. 候选标题与成品一致性

- 菜名中的主要食材集合必须是 `used_items + allowed required_extra_items` 的子集；
- 标题不得出现 `unused_items`；
- 卡片上显示的 template、槽位、食材、克数、所需补充和时间必须与最终生成使用的 plan 完全相同；
- DeepSeek 不得在成品阶段重新选择候选、换槽位或引入额外主料。

## 8. 换一换契约

换一换是“换一个有效 plan”，不是换一句模型文案。

- 换一换只重新运行 Planner，不调用 DeepSeek；
- 当前 plan 对本次换一换硬排除；
- 更早历史只做软降权，避免候选永久耗尽；
- 新计划必须至少改变 `template_id`、槽位分配、主食/烹饪形态之一；
- 新计划仍须满足覆盖、安全、时间和补充项契约；
- 找到计划后，用户确认才调用 `/generate-plan`；
- 没有同等承诺的第二套计划时，在 2 秒目标内返回 `no_alternative_plan`；
- 前端保留当前菜并显示「当前组合只有一个可靠的一锅方案」，提供修改食材入口；
- 不为换一换调用模型，不等待二十秒后才宣告失败。

## 9. 确定性表达层与零漂移校验

### 9.1 调用边界

2026-07-29 的真实 Chrome 手机旅程显示：用户确认方案后，成品步骤可见仍需 23.5–47.35 秒。与此同时，当前 contract 已把模型限制为从 `dish_name_options`、每步 `allowed_texts` 和 `recommendation_reason_options` 中原样选择，模型不再拥有可交付的创意空间。

因此 Preview 默认使用 `generationMode:"deterministic"`：

- `/generate-plan` 服务端重算并锁定计划后，由本地确定性表达器从人工受控短语中稳定选择；
- 整个 V2 旅程调用 DeepSeek 次数为 0，不读取生成预算，不要求 API key；
- 仍完整运行现有计划一致性、零漂移、食材边界和安全终点校验；
- 失败不自动重试，也不静默回退旧选择器；
- `generationMode:"llm"` 路径保留，供对照和可逆回滚，但不是第一轮 Pilot 默认路径。

Planner 决定并锁定：

- `template_id`；
- slot assignment；
- 用户食材使用集合；
- required extra items；
- 每项克数；
- Ratio DSL 计算出的液体和比例；
- cooking order；
- safety endpoints。

表达器只能输出：

- 用户看到的菜名；
- 自然语言步骤；
- 推荐理由。

这些文字必须来自人工维护的有限目录：每个 active template 的菜名风格和推荐理由、每个 cooking action 的步骤句式与过渡语都必须预先写入受控代码；表达器只能按锁定槽位填入占位符，不得自由拼接新的烹饪事实。

### 9.2 确定性越界校验

生成后必须逐项对账：

- 主要食材集合与计划完全一致；
- 每项食材克数与计划完全一致，允许方差为 0；
- 比例和液体不得偏离 Ratio DSL；
- 不得改变生熟状态或部位；
- 不得新增、删除或替换主要食材；
- 安全终点必须完整保留。

语言表达可在受控选项内稳定变化，计划事实不允许漂移。任何越界都必须明确失败并保留已确认计划；不自动重试。确定性模式不产生付费调用。

## 10. 旧路径兼容与回滚

- Preview 使用明确的环境开关启用 V2「直接推荐」；
- Preview 构建同时使用 `generationMode:"deterministic"`；缺失或非法构建元数据时生成模式回退为 `llm`，不得谎报确定性模式；
- 旧选择器保留用于影子对照，不作为用户请求的静默 fallback；
- LLM 表达层代码保留并由构建标志关闭，不删除；
- 若 V2 准入门失败，关闭 Preview 开关并停止发放链接；
- 不在同一用户旅程中途从 V2 偷偷切回旧选择器；
- production 保持不动；
- 该设计不改变旧协议的历史兼容代码，但 Pilot 入口只发 V2 Preview。

## 11. 30 条影子对照与发布门

### 11.1 对照维度

同一组输入分别运行 Planner V2 和旧选择器，记录：

- 食材识别率；
- 最佳候选覆盖数和覆盖率；
- 未使用食材及原因；
- 额外主要食材数量；
- 生熟状态和部位是否被错误改变；
- 兼容性和安全终点；
- 候选之间的真实差异；
- 规划耗时；
- 候选卡与最终生成的一致性。

旧路径通过额外购买主要食材或错误生熟转换得到的“高覆盖”不算优势，必须单独标红进行人工判断。

### 11.2 Preview 硬门槛

30 条旅程全部通过后才发送 Pilot 链接：

- taxonomy 对预期常见食材识别正确；
- 正常候选全部达到覆盖门槛；
- V2 的有效覆盖综合表现不劣于旧路径；
- 额外主要食材为 0；
- 生熟/部位错误转换为 0；
- 候选标题与使用食材矛盾为 0；
- plan 与生成成品的食材、克数漂移为 0；
- 安全越界为 0；
- `/plan-meal` 不调用 DeepSeek，P95 小于 2 秒；
- 从用户选择方案到成品可见的 P95 小于 2 秒；
- 服务器端网络与预算断言证明整个 V2 旅程 DeepSeek 调用为 0、付费预算读写为 0；
- 本轮 Preview 验收请求中 `bad_json = 0`、`5xx = 0`；
- 任何失败都必须有稳定、可理解的页面反馈，不得表现为按钮无反应。

### 11.3 必含真实旅程

1. 鸡腿 + 土豆：2/2 识别和规划；若使用焖面，只允许补面条、水和基础调味；顶层与锅级覆盖均为 1。
2. 虾仁 + 玉米：2/2 被识别，不得静默丢弃。
3. 面条 + 猪里脊 + 白菜 + 香菇 + 胡萝卜：不得展示 2/5 正常卡，不得额外引入鸡肉或土豆；达不到 3/5 时进入诚实逃生状态。
4. 大米 + 牛里脊 + 番茄 + 鸡蛋 + 西兰花：正常候选至少 3/5，标题只含实际使用食材。
5. 番茄 + 金针菇 + 鸡蛋 + 西兰花：不得只使用一种食材；未使用项有理由。
6. 豆腐 + 青菜：两项都被识别，蛋豆腐锅和菌菇蔬菜锅的兼容排序可解释。
7. 剩米饭 + 鸡蛋：只能进入熟饭适配规则，不得套生米比例。
8. 大米 + 虾仁 + 白菜 + 玉米 + 番茄：若只有一个 5/5 可靠计划，换一换立即返回 `no_alternative_plan`，不调用模型。
9. 鸡胸肉 + 土豆 + 洋葱 + 胡萝卜 + 西兰花 + 玉米 + 豆腐 + 鸡蛋：第一轮按 recommend 选择合理子集并诚实显示 unused；不得伪装成完整清库存或展示断裂多锅流程。
10. 模型把牛里脊改成牛腩：确定性拒绝。
11. 模型新增香菇或虾仁：确定性拒绝。
12. 模型修改任一克数：确定性拒绝。
13. 标题包含未使用土豆：确定性拒绝。
14. 无第二计划：当前菜保留，前端展示明确路径。

剩余旅程应覆盖：0/1/2/3/4/5/6/8 种食材、第一轮公开可点击的
quick/normal/batch、常见忌口、未知食材、相同食材不同部位和至少一次可成功换一换。
fresh 继续保留在 Planner 纯函数与 HTTP 契约测试中，但第一轮 Pilot 页面按既有
止损决定不开放该入口，因此不得把不可点击的 fresh 冒充真人浏览器旅程。

## 12. 5 人 Pilot 设计

### 12.1 招募与发放分离

- 可以立即招募、约时间和说明测试方式；
- 在第 11 节所有 Preview 门槛通过前，不发送链接；
- 真实用户不是已知硬伤的免费 QA。

### 12.2 每位用户记录

```text
用户编号 / 日期：
输入食材：______
首道候选覆盖：x/N
选择了哪道：______
做完了吗：做完 / 做到一半放弃 / 没开始做
卡在哪一步：______
点过几次换一换：__
有没有按钮没反应：有 / 没有
候选是否变差：没有 / 有（原组合：______）
第二天愿意再用吗：愿意 / 不愿意
用户原话：______
你有没有想过一次把冰箱里的东西都用完？当时怎么办的？
原话：______
```

不增加账号或埋点，优先记录用户原话和真实做饭结果。

### 12.3 判断标准

- `≥ 3/5` 第二天愿意再用：通过，按失败组合做下一轮定向优化；
- `1–2/5`：逐条复盘没做成和换一换变差的旅程；
- `0/5`：停止扩内容，重新审视首屏和核心承诺；
- 是否真正做完一顿饭作为关键解释指标单独记录，不用点击代替。

Pilot 期间冻结版本，除 P0 安全或完全阻断外不修改代码，以免污染结果。

## 13. 实施顺序

1. **现在即可进行，非代码**：招募 5 人、约测试时间，但不发链接。
2. 补齐 taxonomy，并修复覆盖率单一语义和响应一致性。
3. 将 Preview 的「直接推荐」接到 `/plan-meal`，候选页不调用 DeepSeek。
4. 落实候选覆盖门槛、诚实逃生口、允许补充项和卡片一致性。
5. 将换一换切到 Planner，并实现 `no_alternative_plan`。
6. 将 `/generate-plan` 接到确认计划，用人工受控文案做确定性表达，并继续执行食材、克数与安全零漂移校验。
7. 跑 30 条影子对照和真人浏览器点击旅程，满足全部发布门。
8. 发送 Preview 链接，开展只含「直接推荐」的 5 人 Pilot。
9. 根据真实输入和失败组合，定向扩展 taxonomy、模板规则和中国菜饭 evidence。
10. 只有 D2 回访证明用户确有清库存需求时，另立规格实现完整多锅状态机。

## 14. 后续决策边界

Pilot 前不通过想象补大量中国地域菜谱。Pilot 后的扩展顺序为：

1. 真实用户输入中未识别的高频食材；
2. 有合理一锅组合但当前模板无法承接的槽位规则；
3. 真实发生的换一换深度缺口；
4. 中国菜饭和地域做法只作为技法、安全、比例和来源 evidence，不能重新成为固定组合空间的上限。

若 D2 没有出现清库存需求，不启动有状态多锅。若需求明确，再单独恢复 pantry 的 `must_use` 全覆盖契约和最多三锅状态机，不与本轮 Pilot 混做。

## 15. 方案取舍记录

### 采用

- 确定性 Planner 作为直接推荐主线；
- 候选规划零 DeepSeek；
- 确定性本地表达作为 Preview 默认生成模式；
- 保留构建标志关闭的 LLM 表达路径，确保可逆；
- 每个 template/action 使用人工受控文案，不让字段自由拼接生成烹饪事实；
- 只生成已确认计划；
- Ratio DSL 和食材克数零漂移；
- 招募与发链接分离；
- 第一轮只开放直接推荐；
- 用 30 条影子对照和真人点击作为发布门。

### 拒绝或延期

- 继续修补旧选择器：只能缓解表象，无法解除固定 recipe 组合上限；
- Pilot 前广泛扩菜谱：没有真实输入依据，并会推迟核心假设验证；
- 立即开放残缺清库存：违反全部覆盖承诺；
- 静态第二锅建议：不能替代连续状态机；
- 自动回退旧路径：会掩盖失败并污染验证；
- 允许模型克数小幅漂移：Planner 已确定比例时，任何漂移都是越权。
- 默认继续调用模型从有限选项中做零创意选择：实测增加 23.5–47.35 秒等待、费用和失败面，却不增加用户价值。
