# 一锅出真实菜饭目录：搜集期执行规范

日期：2026-08-05  
状态：搜集期规范，已获产品负责人确认；不授权修改运行时、合并 PR 或部署 production

## 1. 目标与边界

本阶段只扩大“真实、有出处的一锅出/菜饭”研究资产。目标是让未来的用户看到真实存在的菜名、地域或菜系身份和可追溯事实，而不是把用户食材自由拼成一个听起来像菜名的组合。

本阶段允许新增或补充结构化目录中的 `identity_verified`、`recipe_fact_checked` 条目；不因搜集放量晋升 `executable`，也不绕过逐条人工签署和厨房验证。

明确不做：

- 不修改 `index.html`、Worker、代理、Planner、模板、Ratio DSL 或 DeepSeek 契约；
- 不新增账号、用户画像、营养追踪、埋点或多 Agent 运行时能力；
- 不把候选菜名交给模型自由改写，不生成没有外部出处的“食材+焖饭”名称；
- 不部署 Preview/production，不把研究目录直接当作用户可见菜单。

现有目录的产品边界继续以[真实出处菜谱目录设计](2026-08-02-source-backed-one-pot-recipe-catalog-design.md)为准。本文件只补充搜集期的执行纪律。

## 2. 收录线

### 2.1 最低收录线

候选必须是具名的一锅出或菜饭，并至少有一条第 1–5 级、可直接打开的外部来源，能够证明菜名、地域/菜系身份或正式厂商配方名称。达到此线登记为 `identity_verified`。

### 2.2 目标收录线

若直接来源还明确记录了核心食材结构和关键技法流程，登记为 `recipe_fact_checked`。用量、米水、时间、安全或器具适配没有证据时保留 `null`，不补猜测，也不因此否定真实身份。

### 2.3 不收录/另册登记

- 只有搜索摘要、聚合转载、社交帖或 RecipeDB 线索，没有可打开一手页面的：只登记到研究缺口表，不写入权威目录；
- 熟米饭炒饭、烩饭、泡饭等二次烹饪：登记到“剩饭一锅候选”另册，待首批目录闭合后再决定是否启用；具名、来源充分的例外不得与生米菜饭混为一类；
- 面条、焖面、汤面、普通汤锅/炖菜、甜米食、后组装盖浇饭：不进入本目录；
- 只有本项目拼接出来的名称或组合：拒绝并记录原因。

“尽可能多”不是“穷尽互联网”的宣称。每批必须记录检索范围、日期、覆盖的地域/家族/厂商线和已知空白。

## 3. 来源与事实纪律

来源优先级保持：政府/地方志/标准与文化机构 > 原始授权资料/书籍 > 厂商正式说明书或官方食谱 > 大学/医院/行业机构 > 可信原创媒体。聚合站、搜索摘要和 RecipeDB 只作发现入口。

每条来源必须只声明它实际支撑的 `claim_scopes`（`identity`、`ingredients`、`quantity`、`liquid`、`process`、`appliance`、`time`、`safety`）。不得因为某来源“看起来像完整菜谱”就把所有 scope 都挂上。

搜集阶段也要尽量记录：

- `evidence_tier`：已知等级就填；未知不能当作高等级；
- `access_status`：直接读取正文/PDF 才可记 `opened`；
- `evidence_locator`：网页段落、行号、PDF 页码或表格位置；
- PDF 的本地凭证页和 SHA-256：只有归档后才可用于后续合同门禁；
- 来源冲突：并列记录，不取平均、不拼成第三套配方；原产地/原技法来源优先，分歧保留为缺口。

不同来源可以共同闭合事实，但每个数字、顺序和安全要求必须能回指具体来源。搜集人员只提取事实和高层结构，不复制原文步骤、图片或版式。

## 4. 三条并行搜集线

每条线独立提交证据包，不能直接编辑 `source-backed-one-pot-recipes.v1.json`：

1. **厂商线**：象印、松下、东芝、大同、飞利浦、九阳、美的、苏泊尔、Tefal、锅宝等官方说明书和食谱库；优先收录公开、参数完整、明确使用米和配菜同锅/连续成饭流程的具名配方。
2. **官方/机构线**：台湾农粮署、县市政府、文化/非遗机构、香港煤气公司、赛马会、医院/大学等直接页面或 PDF；优先菜饭、炊饭、油饭、煲仔饭、抓饭及有地域身份的米饭主餐。
3. **地域/家族线**：按地域 × 技法家族补深，优先江浙沪、闽台、粤港、西北、云贵、川渝、东北/华北等既有空白和高频家庭组合；发现具名炒饭只进另册，不混入生米目录。

每批 20–30 道封顶。三条线可以并行搜集，但入库批次由一个整合者统一去重、分级和版本 bump。

## 5. Agent 任务卡

每个 Agent 收到一张明确任务卡，格式固定：

```text
方向：厂商 / 官方机构 / 地域×家族
范围：指定站点、地域、菜饭家族和检索日期
目标：8–15 条候选（不足时如实报告）
排除：无独立出处、自由组合、面/汤/甜食、搜索摘要独证
交付：只交证据包，不改 JSON、不改运行时、不提交代码
```

每条候选的证据包至少包含：

```json
{
  "candidate_name": "来源中的真实名称",
  "aliases": [],
  "region_or_family": "来源明确支持的地域/家族",
  "source_url": "https://…",
  "source_title": "页面或文档标题",
  "access_status": "opened",
  "evidence_locator": "网页段落、行号或 PDF 页码",
  "evidence_tier": 1,
  "proves": ["identity", "ingredients", "process"],
  "core_ingredients_as_stated": [],
  "known_gaps": [],
  "duplicate_or_variant_notes": ""
}
```

Agent 不得把“建议补充的食材”、模型推断、另一版本的水量或项目适配参数写入 `core_ingredients_as_stated`。未打开的链接只能进入缺口表。

## 6. 整合、去重与状态

整合者逐条对照现有目录和别名表：

- 同名、同核心结构、同技法且只是份量差异：保留一个身份，差异作为来源变体；
- 核心食材、器具技法或地域身份不同，且有独立出处：保留为独立条目并说明关系；
- 厂商适配版不能冒充地域传统身份；传统原方与电饭煲适配版分开记录；
- 来源不足的候选不因“很像”而合并到已有菜名；保持 `identity_verified` 或缺口表。

每次结构化目录变化必须 bump `catalog_version`。批次不得把 `recipe_fact_checked` 改成 `executable`；任何晋升另走人工签署报告。

## 7. 批次报告与提交纪律

每个批次当天完成一次报告和 Git commit，报告必须包含：

1. 旧/新 `catalog_version`；
2. 状态分布变化；
3. 新增和晋升的完整清单（不能只报数量）；
4. 按地域、家族、来源 tier 的分布；
5. 去重、别名和变体处理；
6. 未闭合事实、无法打开来源和待补证清单；
7. 运行的 validator、目录检查、数据测试结果。

提交按内容分开记录（如 `data:`、`docs:`、`test:`），但不得把搜集结果长期留在未提交工作区。工作区若有与本批无关的修改，必须先停下并报告，不得用脏工作区构建或提交。

## 8. 节奏、停止与下一阶段

搜集期时间盒为 3 周（至 2026-08-31），250–300 条只是参考线，不是 KPI。若连续两批新增合格候选少于 10 条，停止继续放量，转入去重、事实闭合和厨房验证。

搜集期结束后才选择首批 `executable`/`kitchen_observed` 菜谱和极简“给我一道”页面。用户最终看到的是厨房验证过的少量真实菜谱，不是研究目录中的全部条目。

## 9. 每批验收清单

- [ ] 候选具名且有独立外部出处；
- [ ] 来源已直接打开，摘要未被当作事实证据；
- [ ] `claim_scopes` 只覆盖实际证明范围；
- [ ] 未混拼不同版本的米水、流程、时间或器具事实；
- [ ] 状态仅为 `identity_verified` 或 `recipe_fact_checked`；
- [ ] 已做名称/别名/地域/技法去重；
- [ ] 20–30 道批次上限未超；
- [ ] 版本号已 bump，报告列出完整新增清单；
- [ ] `node tools/check-source-backed-one-pot-catalog.mjs`、专项测试和 `git diff --check` 全绿；
- [ ] 没有改运行时、Planner、DeepSeek、部署配置或 production。
