# 一锅出创业研发工作台设计

日期：2026-08-29

状态：已在对话中确认产品方向、日常流程和技术边界，待书面规格复核

首版范围：内部自用、research/calibration 构建、本机数据

## 1. 背景与产品判断

用户在《2026-08-17 中式菜饭创业项目》中提出：以标准化中式菜饭为核心，先通过家庭研发与线上内容验证，再进行小范围试吃、配送或餐车测试，最后才考虑门店；研发难点集中在食材搭配、克重、水量、投料顺序、火候、器具、营养和出餐标准化。2026-08-24 的补充把“一锅出”扩展为满足碳水、蛋白质和膳食纤维的一餐式主食；2026-08-25 又明确现阶段的小工具应首先服务本人内容创作和创业前期研发，而非面向公众商业化。

当前代码已经拥有 923 条来源记录、来源执行卡、逐步试做页、权威营养底座、正式化矩阵和厨房观察契约，但这些能力分散在资料库与工程门禁里。现有浏览器试做记录只能保存一组自由文本，不能表达多次实验、版本比较、内容产出或创业阶段决策。

因此首版不继续扩建面向普通用户的菜谱 PWA，而是在现有事实底座之上增加一个独立的“创业研发工作台”。它的核心对象不是菜谱数量，而是一个菜品从想法到可试卖所积累的证据。

## 2. 目标与成功标准

### 2.1 目标

工作台帮助创始人每天完成一条真实闭环：

```text
选择一个候选
  → 制定本次试做计划
  → 在厨房记录实际执行
  → 复盘并决定下一版
  → 生成有事实依据的内容素材
  → 积累为未来试吃和试卖可复用的数据
```

首版成功不以收录量、页面浏览量或营养数字多少衡量，而以以下事实衡量：

1. 能在手机上从零建立“大番茄饭”原创实验并完成一次结构化试做。
2. 能从 923 条来源记录选择一道菜，保留来源事实，并建立不污染来源的改造实验。
3. 能保留同一项目的多次尝试，清楚比较哪次改变了什么、结果如何。
4. 完成复盘后能得到一张研发结论卡和一张不虚构经历的内容素材卡。
5. 刷新页面、关闭浏览器后仍能恢复；能完整导出、校验并重新导入。
6. 默认 production runtime 构建不携带工作台或任何私有研发记录。

### 2.2 非目标

首版不做：

- 顾客点餐、在线支付、配送调度或门店 POS；
- 账号、云端同步、团队协作或公开分享未完成实验；
- 全天饮食追踪、长期营养画像或医疗建议；
- 自动发布自媒体内容；
- 完整成本核算、定价和批量备料系统；
- 用 AI 猜测来源缺失的克重、液体、时间、安全终点或营养权威值；
- 因为完成了一次试做就自动晋升 Planner 或 production approved。

成本、定价和试卖备料是下一个业务模块，但必须复用本设计的项目、尝试和实测产量，不能另建一套数据真源。

## 3. 产品结构

### 3.1 独立入口

新增 `/lab/`，名称为“一锅出研发工作台”。它只进入 `research` 和 `calibration` 构建，不进入默认 `runtime` 构建，不替换现有首页、来源资料库或正式运行目录。

工作台读取现有研究资产，但全部按只读处理：

- `source-backed-one-pot-shelf.v1.json`：搜索、地域、核心食材和来源层级；
- `source-backed-execution-library.v1.json`：来源执行卡和研究起步字段；
- `source-backed-formal-candidate-review.v1.json`：缺口与安全边界；
- `kitchen-trial-catalog.v1.json`：候选合同、器具和安全阻断；
- `foods-tw.json` 与前端权威营养映射能力：营养纠偏。

工作台不能直接改写任何上述资产，也不能通过本机状态授予 Planner、厨房验证或 production 权限。

### 3.2 首页

首页只突出一个主动作：

- 有进行中尝试时显示“继续今天的试做”；
- 没有进行中尝试时显示“选择一道开始研发”。

辅助区域只保留：

- 等待试做的项目；
- 最近完成的尝试；
- 本周鱼、禽、畜、豆项目分布；
- 数据备份状态。

不把 923 张卡直接铺在首页，不做经营仪表盘或虚假的进度激励。

### 3.3 候选选择

候选有两种来源：

1. **来源改造**：从 923 条来源记录创建，固定保存来源 ID、版本、名称、来源层级和建立时的只读来源快照。
2. **原创实验**：从空白概念创建，`origin_type` 明确为 `original_concept`，不得显示传统菜、官方配方或来源已核等表述。

首版预置一个可删除的原创项目“大番茄饭”，仅预置概念、验证问题和内容记忆点，不预填未经试做的精确克重、水量、时间、营养结果或安全结论。

来源候选支持菜名搜索与少量筛选：

- 鱼、禽、畜、豆等实际蛋白质分类；
- 当前设备是否可能适配；
- 来源完整度和现有阻断；
- 地域与一锅形式。

“海基、空基、陆基、豆基”保留为未来顾客可见的品牌语言；内部研发使用具体食材和蛋白质类别，避免语义含混。

推荐只能解释已有事实，例如“来源液体和步骤较完整”“与你登记的设备一致”。不得把内容潜力或健康程度伪装成客观分数。设备未登记或合同不匹配时显示阻断，不静默推荐。

## 4. 研发生命周期

项目状态固定为：

```text
candidate
  → planned
  → cooking
  → reviewed
  → content_ready
  → pilot_candidate
```

任意阶段都可进入 `paused`，但历史尝试不得删除式覆盖。

### 4.1 Candidate

记录菜品假设、想解决的问题、目标使用场景和来源类型。原创项目允许只有概念；来源改造必须绑定来源快照。

### 4.2 Planned

创建一次不可变身份的 `attempt`，填写：

- 计划份数；
- 每项食材名称、状态、目标数量与单位；
- 液体数量或明确水位；
- 器具品牌、型号、容量和程序；
- 计划步骤、投料顺序与预计时间；
- 本次必须观察的问题；
- 与食材风险对应的安全终点。

来源改造默认复制来源执行卡中可用字段，并逐项标注 `source`、`source_hint` 或 `estimated`。用户改动后记录为 `planned`，不再冒充来源事实。

### 4.3 Cooking

手机厨房模式使用大字号、单列步骤和易触达操作。每一步可：

- 勾选完成；
- 记录实际开始/结束时间；
- 修改实际加入量；
- 添加偏差原因；
- 记录临时调整。

实际数据与计划并排保存，不覆盖计划。页面离开或刷新后可恢复当前步骤。

### 4.4 Reviewed

结束试做时必须记录：

- 实际成品份数或重量；
- 干湿、软硬、糊底、出水和熟制状态；
- 味道与食材协调性；
- 操作是否省事；
- 家庭反馈，包括“女儿是否愿意吃”，但允许标记未观察；
- 是否愿意再做；
- 决策：原样复做、修改后再试、暂停。

安全终点缺失、必需步骤未完成或器具身份缺失时，可以保存未完成复盘，但不能把 attempt 标为完成，也不能进入 `content_ready`。

### 4.5 Content Ready

工作台从已记录事实确定性生成两张卡：

**研发结论卡**包含：

- 本次版本和日期；
- 计划与实际差异；
- 成功点、失败点和下次只改什么；
- 真实家庭反馈；
- 尚未验证的事项。

**内容素材卡**包含：

- 一句话选题；
- 菜品视觉或操作记忆点；
- 可陈述的真实试做事实；
- 拍摄镜头清单；
- 需要诚实保留的不确定性；
- 禁止使用的夸张结论。

没有记录过的口感、反馈、用时和营养效果不得生成。首版不调用 LLM；模板输出可复制为 Markdown，不自动发布。

### 4.6 Pilot Candidate

首版只允许人工标记为“试吃候选”，并显示仍缺哪些证据。它不等于可售、production approved 或可以进行公开营养宣称。后续成本和试卖模块将以至少两次可复现尝试、稳定产量和器具合同为输入。

## 5. 数据模型与持久化

### 5.1 分层模型

数据分为四层：

1. `SourceSnapshot`：建立项目时保存的只读来源引用和必要快照；
2. `ResearchProject`：长期菜品假设、来源类型、分类和当前阶段；
3. `Attempt`：一次计划、厨房执行、复盘和内容卡；
4. `WorkbenchSettings`：本机设备清单、导出信息和界面设置。

关键不变量：

- 来源事实不可由计划或实测覆盖；
- 每次 attempt 都有独立 ID、创建时间和版本；
- 实际值只能来自用户输入或可验证的计时事件；
- 内容卡只能引用当前 attempt 中存在的字段；
- 营养项同时保存匹配身份、来源代码和 `estimated` 状态；
- 项目阶段是尝试结果的投影，不能反向伪造尝试证据。

### 5.2 本机存储

使用 IndexedDB 保存结构化记录，数据库名和 schema version 固定。提供独立存储适配器，业务逻辑不得直接调用 IndexedDB，以便测试和未来替换存储实现。

导出文件包含：

- 导出格式版本；
- 导出时间；
- 项目、尝试和设置；
- 每个集合的数量；
- 用于发现截断或损坏的内容摘要。

导入先完成 schema 校验、摘要校验和差异预览。默认按稳定 ID 合并；发生冲突时保留本机版本和导入版本，由用户选择，不允许静默覆盖。

### 5.3 旧记录迁移

首次启动检测 `yiguochu-source-recipe-trials`：

- 每个旧 `recipe_id` 建立一个来源改造项目；
- 旧自由文本形成 `legacy_import` attempt；
- 无法结构化解析的内容保留原文，不猜单位和字段；
- 迁移成功后保留原 localStorage，直到用户完成一次有效导出；
- 重复启动必须幂等，不产生重复项目。

`yiguochu-cook-mode:*` 只代表步骤勾选，不足以证明真实试做完成；可恢复到进行中状态，但不能自动生成已完成 attempt。

## 6. 营养、安全与来源边界

- 营养继续遵守“台湾食药署库 → 前端权威库 → 未命中标估算”的既有优先级。
- 计划营养和实际营养分别计算；只有实际称量完整时才展示“本次实测配方营养参考”。
- 不展示全天达标判断，不根据身高体重给医疗化摄入建议。
- 油、糖、盐、酱油和酱料不能被当作零贡献香辛料忽略。
- 涉及禽、猪、海鲜、鸡蛋等风险时，必须从现有安全合同读取必要终点；不存在匹配合同时 fail closed。
- 内容卡不得生成“促进吸收”“改善菌群”等健康结论，除非未来建立独立证据与合规审查层。
- 来源改造始终能回看来源链接、来源事实、研究估算和本次实际值；四者在视觉上不能合并成一个数字。

## 7. 代码边界

首版采用小模块而不是继续扩大单文件页面：

- `lab/index.html`：语义结构和入口；
- `lab/styles.css`：移动优先样式；
- `lab/app.js`：路由与界面编排；
- `lab/domain.js`：状态转换、不变量和内容卡生成；
- `lab/storage.js`：IndexedDB、导入导出和迁移；
- `lab/data.js`：只读研究资产加载与连接；
- `tools/data/founder-research-workbench.schema.v1.json`：导出与核心记录契约；
- `tools/lib/founder-research-workbench.mjs`：Node 侧校验和确定性规则。

浏览器与 Node 共享的纯业务规则不得复制两套。如无法直接共享模块，应把权威规则放在无 DOM、无 Node 专属依赖的 ESM 中，由两端共同导入。

`tools/build-dist.mjs` 仅在 `research` 或 `calibration` scope 复制 `lab/`；service worker 也只在这些 scope 缓存工作台 shell。任何默认 runtime 构建出现 `/lab/`、研发 schema、研发导出或私有记录都视为测试失败。

私有记录只存在浏览器 IndexedDB 和用户主动下载的文件中，绝不被写入 `dist/`、Git 或 Worker 日志。

## 8. 异常与恢复

- 研究资产加载失败：已有本机项目仍可打开，来源项目标记“来源暂不可核对”，禁止创建新来源快照。
- IndexedDB 不可用：明确进入只读/临时模式，并提示立即下载当前数据；不能显示“已保存”。
- 页面意外关闭：保存当前 attempt 和步骤位置；恢复时明确提示仍是未完成试做。
- 来源记录被更新或移除：保留创建时快照，显示当前版本差异或“已脱离当前目录”，不丢历史。
- 导入格式未知、摘要不符或字段非法：拒绝写入并给出可读错误；原本机数据不变。
- 多标签页同时修改：以记录版本做乐观并发检查，冲突时要求选择，不做最后写入者静默覆盖。
- 营养匹配不确定：显示估算或待匹配，不做模糊权威命中。

## 9. 验证策略

所有实现采用 TDD。测试至少覆盖：

### 9.1 领域单元测试

- 合法与非法阶段转换；
- 来源、计划、实际值不可互相覆盖；
- 一次 attempt 的版本与差异生成；
- 安全终点和设备缺失时不能完成；
- 内容卡只使用已记录事实；
- 原创概念不获得来源或传统身份；
- 营养估算标记不被移除；
- 旧 localStorage 迁移幂等。

### 9.2 存储测试

- 创建、更新、刷新恢复和多 attempt；
- 导出 → 清库 → 导入后语义等价；
- 损坏摘要、未知版本和 ID 冲突 fail closed；
- 多标签页版本冲突；
- 旧记录原文无损保留。

### 9.3 浏览器旅程

1. 打开空工作台并创建“大番茄饭”；
2. 填写设备、计划、步骤和安全终点；
3. 在厨房模式记录实际偏差并完成复盘；
4. 生成研发结论卡和内容素材卡；
5. 刷新后恢复完整状态；
6. 从来源库建立一个改造项目并回看四层信息；
7. 建立第二次 attempt，比较改动；
8. 导出、清空测试数据库、导入并恢复；
9. 手机视口无横向滚动，主要操作单手可触达。

### 9.4 构建边界

- research/calibration 构建存在 `/lab/` 且依赖齐全；
- runtime 构建不存在 `/lab/`、工作台 schema 或研发私有数据；
- `node tools/check-recipes.mjs` 和现有 Planner/菜谱门禁继续通过；
- service worker 的 shell 与当前 artifact scope 一致。

## 10. 首版验收清单

以下全部满足才算首版完成：

1. `/lab/` 在 research preview 可打开，首页主动作是“继续今天的试做/选择一道开始研发”。
2. 可创建原创项目和来源改造项目，两种身份不可混淆。
3. “大番茄饭”仅预置概念和验证问题，没有伪造实验参数。
4. 一次 attempt 能完整经历计划、厨房执行、复盘和内容卡生成。
5. 同一项目可创建并比较至少两次 attempt，历史不被覆盖。
6. 缺设备或必要安全终点时不能误标完成。
7. 营养数值保留权威来源或估算标识，实际称量不完整时不伪称实测配方。
8. 内容素材不包含未记录口感、反馈、时间或健康效果。
9. 旧试做记录可幂等迁移且原文无损。
10. 刷新恢复、导出、校验、差异预览和导入通过自动化旅程。
11. 手机视口通过可用性检查。
12. runtime 构建中不存在工作台和私有研发资产，现有菜谱门禁无回归。

## 11. 后续演进顺序

首版积累真实尝试后，按以下顺序扩展：

1. **内容模块增强**：从真实记录生成不同平台的内容草稿，但仍需人工确认，不自动发布。
2. **成本与定价**：增加食材采购价、损耗、批次成本、单份成本和目标毛利；不把家庭估价当正式经营账。
3. **小范围试吃**：匿名反馈、份量、复购意愿、配送保持性和批次复现。
4. **试卖备料**：在稳定配方和真实成本基础上生成批量称量与设备容量校验。
5. **顾客选餐**：只有线下测试证明四类基底与选择流程有效后，才建设顾客端小程序。

线下门店、账号画像、全天营养推荐和发酵食品商业组合均需另立验证假设，不在本工作台首版中顺带实现。
