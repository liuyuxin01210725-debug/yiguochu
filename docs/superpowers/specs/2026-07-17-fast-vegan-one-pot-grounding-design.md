# Phase A 快速纯素一锅菜谱与生成契约加固设计

日期：2026-07-17
状态：设计已获用户口头确认，等待书面规格复核后进入实施计划

## 1. 背景

Phase A 当前保留 9 个菜谱家族和 12 道 `approved` 基础菜谱。最近对 6 个 known-gap 场景进行单次在线检查后，暴露出三个与本设计直接相关的问题：

1. `mung-bean-brown-rice-curry` 的原始来源虽然是一口锅，但总时长约 45 分钟，与产品希望用户较快吃上饭的定位冲突。
2. `lentil-potato-tomato-curry` 的原始来源使用两个烹饪容器；当前基础菜谱没有把“单锅改编”及改编步骤表达得足够透明，模型仍可能生成“另起一锅”。
3. 比例规则虽然进入 grounding，但模型可能用未计量的泡发水、浸泡液或笼统的“适量水”绕开精确液体比例。

此前已经完成两项独立修复：有界恢复 JSON 尾逗号，以及识别“另一个小锅”等第二口锅措辞。本设计不重复这些工作，只在它们之上加固可信菜谱底稿和生成契约。

## 2. 目标

本次实现必须同时满足以下目标：

1. 用一份来源可追溯、原始做法即为一口锅、总时长约 30 分钟的纯素主餐，替换不够快的绿豆糙米菜谱。
2. 保持 9 个菜谱家族、12 道 `approved` 基础菜谱，不开始 150–200 道扩展。
3. 将扁豆土豆番茄咖喱明确改写为同一口锅完成，并向用户说明它是基于来源菜谱的单锅改编。
4. 让生成请求明确量化所有留在成品中的液体，不允许用未计量浸泡液规避比例。
5. 将普通 `quick` 目的的诚实时长阈值从 25 分钟统一为 30 分钟，避免系统逼迫约 30 分钟的来源菜谱虚报时长；用户主动选择“想更省事”时仍保持 25 分钟的更严要求。
6. 不增加 DeepSeek 请求次数，不增加新的自动重试，不在服务器端偷偷改写模型给出的食材克数或步骤。
7. 完成离线回归后，严格按“6 个 known gaps → 30 个 live smoke → 移动端人工评审”的顺序验证；任何前置闸门失败都停止后续在线调用。

## 3. 非目标

本次不做以下工作：

- 不接入 RecipeDB 或复制其内容；RecipeDB 仍只可用于研究。
- 不扩展到 150–200 道菜谱。
- 不建立用户行为收集、点击分析、账号或推荐画像。
- 不手工编造大豆蛋白块、营养酵母等食材的营养数据；权威库未命中时继续诚实标记为估算。
- 不为任意克数比例实现复杂数学解析器；这两个 numeric-ratio known gaps 仍保留人工复核。
- 不改变现有前端重试策略，不新增后台调用或模型失败后的隐形补请求。
- 不部署到 production `main`，也不提升 preview 为生产版本。

## 4. 核心设计决策

### 4.1 替换基础菜谱

删除以下 `approved` 基础菜谱：

- ID：`mung-bean-brown-rice-curry`
- 名称：绿豆糙米蔬菜咖喱锅
- 原因：原始来源约 45 分钟，不适合作为本阶段的快速基础菜谱。

新增以下 `approved` 基础菜谱：

- ID：`soy-lentil-vegetable-stew`
- 名称：大豆扁豆西兰花炖锅
- 家族：`family-legume-vegetable-stew`
- 形式：炖锅
- 菜系说明：家常纯素炖锅
- 用途：`quick`、`pantry`、`batch`
- 总时长基准：约 30 分钟
- 来源标题：`Cookbook:Soy-Lentil-Vegetable Stew`
- 直达来源：<https://en.wikibooks.org/wiki/Cookbook%3ASoy-Lentil-Vegetable_Stew>
- 许可：`CC BY-SA 4.0`
- 署名：`Wikibooks contributors, Cookbook:Soy-Lentil-Vegetable Stew`
- 获取日期：`2026-07-17`

来源原始配方按 1 大份给出 40 克大豆蛋白块、80 克红扁豆、250 克冷冻西兰花和约 500 毫升沸水，并明确使用同一口锅完成。生产菜谱保留这组结构和数量关系，按用户份数等比例缩放。

菜谱数据增加 `total_time_minutes: 30`。该字段为可选字段，但出现时必须是 1–60 的整数，并进入可信 grounding。普通 `quick` 的 Worker 提示和前端质量评分同步采用 30 分钟阈值；不得为了通过现有 25 分钟评分而让模型虚报。`SWAP_HINT.easier` 代表用户主动要求“更省事”，继续保留 25 分钟阈值，不随本次调整放宽。

核心食材：

- 红扁豆
- 大豆蛋白块
- 西兰花
- 红洋葱

可选食材：

- 橄榄油
- 蒜
- 营养酵母
- 花生
- 葵花籽
- 黑胡椒、姜黄、辣椒、葛缕子、姜等香料

花生不得成为固定核心。结构化替换位必须明确：花生只能替换为葵花籽，或者不加坚果/种子；当用户填写花生过敏或不吃花生时，花生必须从食材和步骤中同时排除。模型不得自行把其他未批准坚果当作等价替换。

这道基础菜谱自身不得包含肉类、禽类、鱼虾、鸡蛋、奶制品或蜂蜜。用户选择 `vegan` 时，grounding 和通用饮食限制共同约束输出；但本阶段仍不宣称已经有确定性的纯素违规检测器，最终以 known-gap 人工复核为准。

### 4.2 家族数量与分布

新菜谱归入现有 `family-legume-vegetable-stew`，不创建第 10 个家族。原 `family-rice-legume-pot` 仍有 `chicken-black-eyed-pea-stew`，所以 9 个家族都继续至少包含一道菜谱，总菜谱数保持 12。

内部家族 ID 和已有其他菜谱 ID 不重命名，避免制造与本次目标无关的迁移范围。

### 4.3 扁豆土豆番茄咖喱的单锅改编

保留：

- ID：`lentil-potato-tomato-curry`
- 来源：<https://en.wikibooks.org/wiki/Cookbook:Lentil,_Potato,_and_Tomato_Curry>
- 现有 `rice-allergy-complete-main` 资格

但生产底稿必须从“两容器原始做法”改为以下单锅顺序：

1. 在同一口锅中用植物油炒香土豆和香料。
2. 加入番茄、红扁豆和已量化的水。
3. 加盖炖至红扁豆软烂、土豆中心无硬芯，全程不倒锅、不预煮扁豆、不另起平底锅或小锅。

`summary`、`technique` 和 `ratio_rules` 都必须与这条顺序一致，不能继续保留“扁豆先煮、土豆另煎”的旧表述。

为满足来源透明度，菜谱增加结构化 `adaptation_note`，内容明确说明：原始来源使用两个烹饪容器，一锅出将其改为同锅先炒后炖。该字段进入 Worker grounding，并由服务器覆盖写入顶层响应字段 `adaptation_note`，随现有来源信息展示给用户。模型返回的同名字段不可信，必须在附加服务器元数据时被可信菜谱值覆盖；没有改编说明的菜谱统一返回空字符串。来源标题、URL、许可和原作者署名继续保留，不能把单锅改编伪装成来源原文。

菜谱库里的 `adaptation_note` 为可选字段，但一旦出现必须是 1–400 字的非空字符串。菜谱库校验器负责拦截空值、超长值或非字符串值。前端只读取服务器顶层 `adaptation_note`，经 400 字边界清洗后显示。

### 4.4 液体与比例生成契约

Worker 的可信菜谱 grounding 和最终输出契约增加以下要求：

1. 所有留在成品中的水、高汤、番茄汁、泡发水或浸泡液，都必须在 `ingredients[]` 中有同义食材名和大于 0 的数字 `grams`。
2. 步骤中不得使用未计量的“适量水”“酌情加水”“保留泡发水”等作为主要烹调液体。
3. 浸泡或焯水用水只有在步骤明确写出倒掉、弃去、滤掉或沥干时，才可以不列入成品食材。
4. 如果泡发水保留进成品，就必须计入总液体克数；不能在量化水之外再加入一份未测量的浸泡液。
5. 基础菜谱的比例规则必须同时体现在食材克数和步骤描述中。模型在返回 JSON 前自行核对，但服务器不替模型修改数值。
6. 所有做法继续受“一口烹饪容器”约束；“另一个小锅”“另取平底锅”“第二口锅”等均为失败。

Python 本地代理与 Worker 使用同一语义。涉及通用 prompt、可信菜谱 grounding 或液体契约的改动，必须同步到 `ai_proxy.py`，并用测试证明本地与线上契约没有漂移。

### 4.5 来源与营养边界

菜谱来源负责证明菜名、核心搭配、技法、用量关系和单锅可行性；营养数值仍走项目既有三层机制：

1. Worker 台湾食药署库命中时覆盖并标记权威来源。
2. 前端本地 `FOODS` 命中时使用本地权威值。
3. 两层都未命中时保留 `est=true`。

本次不会因为新菜谱出现大豆蛋白块或营养酵母，就凭常识向 `FOODS` 填入数字。若实施中决定补营养条目，必须另走项目“加新食材 SOP”，逐条记录台湾库 code、USDA FDC ID 或中国食物成分表来源；这不是本规格的完成条件。

## 5. 组件与数据流

### 5.1 菜谱库

`tools/data/recipe-library.json` 是 12 道基础菜谱的权威数据源。它负责：

- 删除旧菜谱、加入新菜谱；
- 保存来源、固定核心、批准替换、关键技法、比例和安全规则；
- 保存扁豆土豆番茄咖喱的 `adaptation_note`。

### 5.2 选择与 grounding

Worker 继续按现有机制根据库存、忌口、用途、最近菜谱和家族进行候选排序。新菜谱不获得隐藏优先级，只靠其核心食材、用途和家族参与选择。

选中后，`buildRecipeGrounding()` 将固定核心、批准替换、禁忌组合、技法、比例、安全规则以及可选的 `adaptation_note` 写入请求。模型只负责在这些边界内生成可执行 JSON。

### 5.3 生成与校验

数据流保持：

`用户条件 → 服务器选择基础菜谱 → 构建可信 grounding → 单次 DeepSeek 请求 → 解析 JSON → 结构/熟制/单锅/食材一致性校验 → 来源与营养补全 → 返回前端`

不在这条链路加入第二个模型、额外检索、自动克数改写或新的重试分支。

### 5.4 前端展示

前端继续显示服务器返回的基础菜谱来源。若服务器顶层返回非空 `adaptation_note`，`mapDish()` 将它保存为 `adaptationNote`，移动端来源区域同时展示简短的“单锅改编说明”，让用户分清原始来源与一锅出的改动。该说明不从模型生成的正文或 `source_refs` 推断。

显示应沿用现有信息层级，不新增首页表单、弹窗或独立复杂页面。

## 6. 错误处理与停止条件

- 菜谱库缺少 approved 来源字段、来源不是 HTTPS、许可/署名/获取日期不完整：`check-recipes` 失败，禁止提交或部署。
- `adaptation_note` 存在但为空或类型错误：菜谱库校验失败。
- 模型返回无法解析的 JSON：沿用现有有界尾逗号恢复；仍无法解析则本次请求失败，不为验证脚本额外重试。
- 生成结果出现第二口锅、未用却列入成品的库存、食材未进入步骤或高风险食材缺少熟制证据：返回 validation 失败，不能把该例计为通过。
- 六个 known gaps 中任意一例请求失败或人工复核不通过：停止，不运行 30 例 live smoke。
- 30 例中任意一例没有 trusted base recipe ID、pairing basis 或存在 validation flags：不得宣称 Phase A exit gate 通过。
- 未完成移动端来源/改编说明检查和 30 例人工评审：不得部署或进入 150–200 道扩展。

## 7. 测试设计

实施必须使用测试先行，至少覆盖以下内容。

### 7.1 菜谱库与校验器

- 旧 ID `mung-bean-brown-rice-curry` 不再存在。
- 新 ID、名称、家族、来源标题、HTTPS URL、许可、署名和获取日期精确匹配。
- 库保持 9 个家族、12 道 approved 菜谱。
- 新菜谱固定核心不包含花生；花生替换只允许葵花籽或不加。
- 新菜谱不包含动物性核心或可选食材。
- 空或非字符串 `adaptation_note` 被校验器拒绝。
- RecipeDB 仍不能成为 production approved source。

### 7.2 选择与 grounding

- 新菜谱能替代旧菜谱进入基线、别名、库存不适合和换菜回归用例。
- 花生过敏时，grounding 明确舍弃花生且不得把它带入食材和步骤。
- `vegan` 场景中，动物性库存被列为舍弃库存。
- 新菜谱 grounding 包含 40:80:250:500 的基准关系、按份数缩放语义、一口锅要求和纯素边界。
- 新菜谱 grounding 包含 `total_time_minutes: 30` 对应的诚实时长基准；普通 quick 的 Worker 与前端阈值都是 30 分钟，31 分钟会被判为超限。
- 扁豆土豆番茄咖喱 grounding 包含 `adaptation_note` 与同锅先炒后炖顺序。
- 模型伪造的 `adaptation_note` 会被服务器可信值覆盖；无改编说明的基础菜谱返回空字符串。
- 通用输出契约包含“所有留存液体必须有数字克数”和“未计量泡发水不得保留”。
- Worker 与 Python 本地代理包含等价规则。

### 7.3 结果校验回归

- “另一个小锅中加热”继续触发 `multi_pot_step`；“无需另一个小锅”不误报。
- 保留泡发水但食材表没有对应水克数时触发结构失败。
- 明确倒掉泡发水时不要求把该水计入成品。
- 食材表有 500 克水且步骤使用这 500 克水时通过液体一致性检查。
- 测试不得实现或暗示服务器自动修正模型克数。

### 7.4 全量离线闸门

依次运行并全部通过：

1. Worker、前端和 Python 相关测试。
2. `node tools/check-foods.mjs`。
3. `node tools/check-recipes.mjs`。
4. 重建并验证 100/100 静态 regression corpus。
5. JavaScript 与 Python 语法检查。
6. 检查用户原有未提交改动没有被覆盖，暂存区只包含本次明确文件。

### 7.5 在线验证

离线闸门全部通过后：

1. 在独立端口启动本次代码，不触碰现有 `localhost:8765` 服务。
2. 对 4 个 diet known gaps 和 2 个 numeric-ratio known gaps 各调用一次，不自动重试。
3. 人工确认纯素、无麸质、一口锅、液体比例和未用库存。
4. 六例全部通过后才运行固定 30 例 live smoke。
5. 更新 `docs/recipe-validation-review.md` 中被替换的菜谱 ID 和名称，逐例人工勾选，不预填通过结论。
6. 用移动视口确认来源署名、搭配依据、这次没用和单锅改编说明清楚可读。

## 8. Git 与部署边界

仓库当前存在用户未提交的生产文件修改。实施时必须逐文件保护这些改动，只提交本任务拥有的差异；任何与 `index.html`、`ai_proxy.py` 或 `worker/src/worker.js` 重叠的编辑，都要证明没有吞掉用户原补丁。

Phase A 只允许部署到非 `main` 的 `recipe-validation` preview branch，且仅在所有离线闸门、6 个 known gaps、30 例 live smoke 和移动端人工检查完成后执行。部署命令的 commit message 必须为 ASCII。

本规格获用户复核，只代表可以编写实施计划，不等于批准部署，更不等于批准开始 150–200 道菜谱扩展。

## 9. 验收标准

只有同时满足以下条件，本设计的实现才算完成：

- 菜谱库为 9 个家族、12 道 approved 基础菜谱。
- 旧绿豆糙米菜谱已移除，新大豆扁豆西兰花炖锅来源完整、原始单锅、约 30 分钟。
- 扁豆土豆番茄咖喱只生成同锅先炒后炖，并对用户展示单锅改编说明。
- 留存液体全部量化，未计量泡发水不能进入成品。
- 不新增 DeepSeek 调用或重试，不进行服务器数值改写。
- 全部离线测试和 100/100 静态 regression 通过。
- 6/6 known gaps 完成人工复核后，30/30 live smoke 与移动端评审全部通过。
- `check-recipes`、来源展示和人工评审表均无缺项。
- 用户明确批准后，才可执行 preview 部署；production 与 150–200 道扩展仍保持关闭。
