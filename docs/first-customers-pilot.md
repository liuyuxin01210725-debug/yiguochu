# 一锅出 first-customers 试用追踪

目标不是“发很多人”，而是验证：真实做饭的人会不会在第二天自己回来再用。

Pilot 入口：等待 `recipe-validation` Preview 发布并通过构建号、性能与三路真人浏览器门后填写。**不得发送 production 链接，也不得在发布门完成前邀请测试者承担 QA。** DeepSeek key 轮换由密钥持有人安排在 production 上线前完成；该安全门不得遗忘，但不阻塞内部 Preview 验证。

## 本周唯一目标

- 找 5 个真实做饭的人，一对一发出试用邀请。
- 拿回 5 份完整记录。
- 关键指标：是否真正做完一顿饭，以及第二天是否愿意再用。
- 通过标准预先锁定：≥3/5 第二天愿意再用；1–2/5 逐条复盘失败旅程；0/5 回到首屏和核心承诺。

## 每位用户记录卡

只记真实输入、真实动作、做饭结果和原话；点击次数不能冒充做饭结果。

```text
用户编号 / 日期：
① 输入食材：______  首道方案：______  用了几种（x/N）：
② 做完了吗：做完 / 做到一半放弃 / 没开始做
   卡在哪一步：______
③ 点过几次换一换：__
   变差了吗：没变差 / 变差了（组合：______）
④ 有没有点了按钮没反应：没有 / 有（当时点了：______）
⑤ 步骤看得懂吗：完全看得懂 / 有一处不懂 / 多处不懂
   原话或看不懂的步骤：______
⑥ 照着做出来了吗：做出来了 / 做到一半放弃 / 没开始做
   和页面预期不一样的地方：______
⑦ 第二天回访：愿意再用 / 不愿意
   原话原因：______
⑧ 你有没有想过一次把冰箱里的东西都用完？当时怎么办的？
   原话：______
```

第⑤–⑧条必须尽量记原话，不转写成“满意/不满意”。“做出来了”必须指真实完成一顿饭，不能用点击“开始做”代替。

已知观察项：若用户自然输入“熟玉米”，原样记录输入、系统识别和候选结果；本轮不提前修改 taxonomy。

## 决策规则

- ≥3/5 第二天愿意再用：通过首轮 Pilot，按失败组合做定向复盘。
- 1–2/5 第二天愿意再用：不扩功能，逐条复盘没做成和换一换变差的旅程。
- 0/5 第二天愿意再用：停止讨论菜谱数量，回到首屏和核心承诺。
- 大家只夸、不做饭或不愿再用：视为未通过，不能用打开、点击或生成次数合理化。
- 频繁失败或等待太久：先修稳定性，不做获客扩张。

## 待验证想法（先记着，别在发出去前做）

pilot 期间冒出来的产品改进。**触发条件没到就不做**——避免在零真实反馈时凭空完善（这是这个项目最大的执行陷阱）。

| 想法 | 触发条件（满足才做） | 备注 |
|---|---|---|
| 一周汇总里显示更全营养（铁/锌/镁/钾/维C/维D），单餐保持 6 项主项 | 有人用满 7 天 **且** 主动反馈想看更全营养 | 数据已全算（在 `d.nutrients`），只差周维度 UI；周维度才有累计、单餐别堆。位置判断是对的，缺的是触发它的真实用户 |
| 看菜谱→做饭的衔接（购物清单 / 复制食材 / 做饭大字模式） | 有人反馈"想做，但中间嫌麻烦没做成" | codex 旅程审查指出的最大断点 |
| 留存钩子（添加到主屏引导 / "明天按你反馈调整"承诺） | 第二天回访率偏低 **且** 用户说"会用但忘了打开" | 留存信号弱、且原因是"忘"时才补 |
| 「一日量」口径决策：逼模型给足 1800kcal，还是改叫"一顿正餐+" | 试用者反馈"量不够吃 / 量正好"的倾向明确后 | 实测模型交付 ~1000kcal(58%)，克数化 prompt 已从 43% 拉到 58%，再往上逼收益递减；三档诚实文案已兜底。本质是产品定位问题，不是技术问题 |
| 首屏价值预览（填表前先看到"你会得到什么样的一锅"示例） | 试用者反馈"一开始不知道这是干嘛的" 或 首次生成前流失明显 | codex 与旅程评审都提过；需要真实第一印象数据才能设计对 |
| 菜系/创新增强（菜系偏好选择、"来个没吃过的"按钮、prompt 推融合菜） | 试用者反馈"菜都差不多 / 不够新" | 现状已实测交付 泰/日/韩/粤/融合(普洱排骨煲仔饭等)，prompt 已有形式轮换+蛋白轮换+排重+换菜系按钮。**✅ 2026-06-25 prompt 级交付并上线**：worker.js 加国际一锅出(印尼/泰/越) + 菜系轮换轴 + 冷拌碗形式。诚实记录：触发者是作者本人、非试用者反馈，pilot 仍一个人没发——护栏属**主动越过**。遗留第二期：recentCuisines/recentForms 硬去重(治"扎堆同一菜系"，线上实测3/3聚到泰式椰浆，需动前端) |
| 发酵品类（泡菜/味噌/纳豆/酸奶/酒酿入菜单，作循证设计的品类） | 留存验证通过后做差异化时，或试用者明确想要 | ⚠️ 循证设计约束（不瞎编的前提）：①益生菌不耐热（>60°C 活菌基本灭活），热菜场景"发酵=健康"不成立，须设计成 出锅后加/凉拌/配餐生食；②发酵物普遍高钠（库实测 辣白菜na498/豆瓣酱na5042），与控钠逻辑冲突需平衡；③库内已有辣白菜(USDA)/纳豆/酸奶/豆豉，生成已实测出现泡菜菜饭——缺的是品类设计不是食材。**✅ 2026-06-25 prompt 级交付并上线**：worker.js 冷拌/发酵碗形式，含益生菌出锅后加(活菌不灭)/钠平衡/三件套热量门槛；实测发酵物稳定出现且从不下锅。同为作者本人触发、非"留存验证通过后"，FOODS 库未动(食材本就齐) |
