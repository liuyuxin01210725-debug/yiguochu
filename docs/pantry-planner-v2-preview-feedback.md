## 目的与边界

本阶段只验证一件事：**确定性 Planner 给出的方案，是否符合真实家庭做饭的直觉。**

本记录不用于证明算法已经正确，也不因为一次偏好反馈立即修改规则。当前阶段：

- 不新增 recipe；
- 不新增 template；
- 不修改 Planner 核心逻辑；
- 不把点击、停留或“看起来不错”当成真实做饭结果；
- 只记录真实输入、Planner 实际输出、用户原话和真实烹饪结果。

本地实验入口：双击 `start.command` 后打开
<http://localhost:8081/?planner_v2=1>。不得将该入口作为公开产品发给用户。

历史记录所用基线（2026-07-24）：`pantry-planner-v2` / `templates-v2-20260724` / `taxonomy-v1-20260724`。下方场景 A–D 的既有输出均属于这份历史快照，不应被改写成新版本的真实结果。

## 真人浏览器缺陷修订边界（2026-07-28，已完成新 Preview 复测）

前一版 `direct-recommend-723a106` 已在 Preview 通过 100 次 `/plan-meal`
性能门，但多路真人浏览器点击发现：候选卡可能只更换补充主食而伪装成不同菜；
生肉和慢熟根茎可能排在熟米饭或面条之后；豆腐步骤出现“整理水油”；
虾仁虽列入计划却没有明确下锅；基础油盐缺少确定用量；直接推荐仍出现无效
“分成两锅”路径；空输入承诺与结果不一致；生成结果缺少返回修改入口。

本轮修订边界：

- 不增加 recipe，不增加 template，不建设新推荐系统；
- 相同 `template_id + 用户食材集合` 的候选只展示一次，不凑满三张卡；
- cooking order 必须由结构化 template phase 决定，Ratio DSL 明确锁定水、油、盐；
- 直接推荐没有替代计划时只保留修改食材路径，不能借未上线多锅能力兜底；
- 空输入不请求接口；生成结果保留修改食材忌口入口；
- 只有全量自动门、Preview 构建三方核对、性能门和真人手机浏览器复测全部通过后，才恢复 5 人 Pilot。

### 当前结论

多食材覆盖已经明显改善：上述三组首卡分别为 `4/4`、`3/4`、`5/5`，
没有“选五种只用一种”。但仍有两个发布阻断：

1. 洋葱槽修复尚未部署并做真人回归；
2. `/generate-plan` 的 DeepSeek 表达层真实等待为 23.5–47.35 秒。

当前 DeepSeek 只从服务端已经锁定的有限短语中选择文字，却承担了全部外部等待。
仅缩短超时、降低 `max_tokens` 或自动重试都不能可靠解决。若产品负责人批准把
V2 表达层改为确定性本地选择，仍可复用现有锁定计划、零漂移校验与安全校验，
同时把该接口改为 0 次 DeepSeek；这是规格变化，批准前不得静默实施。

因此当前结论仍为 **Pilot NO-GO**。PR 保持 Draft，production 保持冻结。

## 2026-07-29 确定性表达层实施记录（尚未部署）

经产品负责人批准，V2 的生成页不再默认把已锁定计划发给 DeepSeek 选择有限短语。当前 Draft 改为：

- `generationMode: "deterministic"` 时，由服务端从每个 template 的人工受控菜名、步骤和推荐理由中稳定选择；
- template、槽位、食材、克数、液体、顺序和安全终点仍完全由 Planner 与 Ratio DSL 决定；
- 组装结果继续经过原有的食材集合、部位、克数、步骤顺序、安全终点和受控文案校验；
- `/generate-plan` 在 key、限流、预算和外部 fetch 之前完成，V2 全旅程为 0 次 DeepSeek、0 次付费预算操作；
- LLM 表达路径不删除，通过 `generationMode: "llm"` 保留作可逆的人眼对照；
- 缺失或非法构建元数据必须回退到 `llm`，不能用无效元数据静默绕过既有成本保护。

这次调整的直接证据是已记录的 23.5–47.35 秒生成等待，而模型在原合同下只能从服务端有限短语中原样选择，实际创意空间为零。当前只是本地实现记录；在全量测试、构建一致性、Preview 两接口 P95、30 条真人浏览器点击和文案人眼检查完成前，结论仍为 **Pilot NO-GO**，production 继续冻结。

### Preview 性能门第一次失败与收敛边界

`direct-recommend-0cdc3b5` 部署后，功能与响应格式均正常，但两轮顺序性能门
都没有达到已批准的成品 P95 `< 2s`：

- 唯一部署 URL：规划 P95 1368.09ms、成品 P95 2487.89ms、成品最大
  8394.46ms；
- 稳定 Preview 入口：规划 P95 1558.62ms、成品 P95 3056.28ms、成品最大
  5121.91ms；
- 两轮均为 `bad_json=0`、非 JSON 0、5xx/网络错误 0。

不能只保留较快样本，也不能因为已经远低于旧模型等待就放宽硬门。诊断确认：
候选页刚刚由服务端计算并返回的权威候选，在用户选择卡片后又被完整计算一次。
本轮仅增加一个按 `ASSETS` 绑定隔离、最多 64 项的进程内权威候选缓存：

- 只缓存服务端自己的完整候选 bundle，返回前后都深拷贝；
- key 是规范化后的完整 Planner 请求，不接受客户端 plan 内容；
- 只有 `plan_id` 确实属于该服务端 bundle 才可生成；
- 缓存未命中、隔离实例变化或请求变化时，仍按原安全契约完整重算；
- 不写 KV、数据库、日志或遥测，不形成云端用户档案。

缓存行为已用先失败后通过测试锁定；它不改变排序、覆盖率、菜谱、模板或
DeepSeek 边界。新的 Preview 仍须重新通过全部本地门、两段 100 次性能门和
真人点击回归。

## 测试方法

1. 优先邀请平时真实参与家庭做饭的人。
2. 测试前只说：“请用家里现有食材试一下这个做饭工具。”不要解释 template、覆盖率或 Planner。
