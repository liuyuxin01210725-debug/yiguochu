### 真人旅程发现并已修复

- `start.command` 原先会把新版菜饭前端与 legacy 代理放在一起运行，导致真实
  `/plan-meal` 请求稳定 400。现在先构建 `rice-meal-v1` 产物、以同一产品焦点
  启动代理，并只通过 `dist/` 提供页面；构建或预检失败时在清理旧服务前停止。
- “鸡胸肉 + 土豆”曾被错误显示为“鸡腿土豆焖饭”。现在只有目标为显式 generic
  身份时才允许 taxonomy generic slot；所有真实命名部位必须精确命中或经过
  `approved_substitutions`。
- 增加 3 人份并打通 UI → schema-v3 请求 → 签名计划 → Ratio DSL → 成品克数，
  不再只增加一个没有后端语义的按钮。
- 未安排原因移除“当前已激活目录”“受控用料”等工程语言，改成家庭用户能理解
  的“现有菜饭还没有适合使用这项食材的可靠做法”。

### 当时产品结论

- 这轮修复解决的是“不能撒谎、不能部位冒充、不能本地启动即报错”；
- 它没有解决菜饭密度。2 道 `preview_ready` 远不足以承接首页常见食材，更不足以
  支撑换一换；
- 下一步不是降低覆盖门槛或恢复自由拼菜名，而是从已经登记的固定来源中逐道补齐
  真实菜名、机器比例、电饭煲顺序和安全终点；来源只证明到哪一层，就只承诺到哪一层；
- 在至少覆盖豆腐白菜、牛肉蔬菜、排骨豆角、咸肉青菜和羊肉抓饭等高频结构前，

任何菜饭已经家庭试做或升为 `preview_ready`。

固定校准对象：高丽菜饭、南瓜饭、咖喱鸡肉饭、懒人焖饭（腊肠什锦版）、牛肉什锦饭、
鲜蔬竹笋饭、什锦鸡饭、鲜香菇饭。每道目前只允许两人份；来源证明菜名、组合与高层流程，
项目自己确定的克数、加水量和跨机型适配必须单独接受厨房反馈。

每次试做按下面结构记录，禁止用自动测试、页面点击或“看起来合理”代替真实结果：

```text
菜饭名 / 日期 / 电饭煲品牌型号：
实际食材与称重：
是否完全按页面步骤：是 / 否（改了什么）：
米饭口感：夹生 / 偏硬 / 合适 / 偏软 / 过湿
蛋白熟制：不足 / 合适 / 过老 / 不适用
蔬菜口感：不足 / 合适 / 过软
味道：偏淡 / 合适 / 偏咸 / 其他
是否完成一顿主餐：是 / 否
下一次是否愿意再做：是 / 否
原话与照片编号：
处理：保留 / 调整项目克数或水量 / 回退阻断
```

任何一道试做失败，只处理该 variant，不以来源存在、自动门全绿或其他菜饭成功为理由保留。
