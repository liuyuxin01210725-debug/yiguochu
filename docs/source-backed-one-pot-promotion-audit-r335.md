# 923 条来源菜饭的正式接入审计（r335）

## 结论先行

- 正式 Planner 基础菜谱仍为 **72 道**：`recipe-library.json` 的 12 道 `approved` + 60 道 `auto_approved`。这不是来源目录的总数，而是已经接入 taxonomy、ratio DSL、编译器、过敏语义和真实旅程门禁的运行时基础集合。
- 来源目录为 **923 条**。本轮已为 **923/923** 条生成研究做法卡；其中 32 条主要由来源合同支撑，844 条是“来源片段 + 明确标注的研究补全”，36 条是估算卡，11 条是身份起步卡。估算卡可以帮助试做，但不等于原文定量，也不等于正式菜谱。
- 研究卡完整度已做成门禁：**923/923** 有数字用量、液体提示、至少 3 步顺序和总时长字段；其中 **922/923** 没有安全阻断，另 1 条河豚身份卡只显示禁止家庭执行的安全提示。624 条带原文用量线索、843 条带原文流程线索、285 条带原文时间线索。没有来源值的部分仍明确标为“研究起步/估算”，不冒充正式合同。
- **46 条**来源记录的固定批量、液体、步骤、总时长、安全和过敏字段已闭合；来源公开门禁可通过 **30 条**。其中 3 条是普通锅/煲仔饭原器具边界，不适合当前电饭煲预览池，因此本轮接入 **25 条预览候选**。
- 这 25 条已写入 `tools/data/source-backed-one-pot-preview.v1.json`，资料库页会标注“预览可照做（来源合同闭合，非 Planner 正式菜谱）”。它们仍需 `kitchen_observed` 后才能讨论生产接入；没有部署到 production，也没有把 25 条伪装成 72 道 Planner 菜谱。

## 为什么不是把 923 条直接塞进 72 道运行时

正式 Planner 不是展示名称和步骤的列表。每道运行时菜谱还必须有：

1. taxonomy 中可识别的食材、状态和切型；
2. 可执行的 ratio DSL（份数变化不能靠模型猜克数）；
3. 一个明确的液体合同和一次投料/中途投料协议；
4. 禽肉、猪肉、牛羊肉、鱼贝、蛋和豆类的安全终点；
5. 过敏标签、营养角色、替换槽和禁配；
6. 电饭煲/锅具适配、编译器动作和真实旅程回归。

来源目录中有 **877 条**仍缺至少一项合同字段，**620 条**缺独立安全终点，**456 条**保留普通锅、煲仔、蒸笼、烤箱或其他原器具边界，不能转换成普通电饭煲参数。另有 93 条只有身份核对、6 条仍是待补证。把这些条目直接标成正式运行，会把估算量、安全假设或器具转换当成来源事实。

## 本轮实际接入

| 层级 | 数量 | 用户可见含义 |
| --- | ---: | --- |
| Planner 正式基础菜谱 | 72 | 进入正式选择/编译/旅程门禁 |
| 来源做法卡 | 923 | 资料库逐条可查看；来源与估算分栏 |
| 来源合同闭合 | 46 | 已有固定批量、液体、步骤、时间、安全、过敏字段 |
| 来源公开门禁通过 | 30 | 可作为公开来源候选，但仍非 Planner |
| 电饭煲/一锅饭预览池 | 25 | 资料库标记预览；保留厂商型号/原器具边界 |
| 仍留在研究/阻塞层 | 898 | 缺口保留，不伪造定量或安全结论 |

验证入口：

- `node tools/build-source-backed-preview-manifest.mjs`
- `node tools/check-recipes.mjs`
- `node --test tools/tests/source-backed-preview-manifest.test.mjs`

`source-backed-one-pot-preview.v1.json` 是预览接入清单，不会绕过正式 Planner 的 72 道基础菜谱门禁。下一批工作应按 25 条预览候选逐条记录厨房试做，再将通过记录迁移到 `rice-meal-catalog` 和 Planner，而不是一次性把 898 条估算卡提升为生产菜谱。
